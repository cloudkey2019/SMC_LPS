**🎯 战役目标**：90天内完成 V1 核心版本上线，实现 45万单 / 450万级 Task 的“按产品族分域”高并发排程，单域计算控制在 30 分钟内。 **🛡️ 架构铁律**：采用**模块化单体架构**，主干遍历流程、具体业务规则与底层排产算法实现 **100% 物理与代码级解耦**；采用**分域隔离计算**，严控单节点内存占用。

## ⚔️ 1号位：计算域核心开发

- **所属领域**：计算域（`SchedulingEngine` 命名空间）。
  
- **核心任务**：开发纯内存排程推演算法。**彻底隔离外界一切业务逻辑与分域编排逻辑**，接收到单一产品域的 Task 快照后，专心攻坚内存图与时间槽寻址，极致压榨单线程 CPU 性能。
  
- **任务包**：
  
  - **底层数据结构研发**：开发 `TimeWindow` 等值类型结构。实现 `IntervalTree`（时间线段树），保障日历空隙的极速检索。
    
  - **优先级队列排序**：解析外围传入的策略配置，对本域内分配到的加工任务进行优先级降序排列。
    
  - **核心推演循环开发**：实现带有时间约束的“倒排”推演，及触发时间边界后的“正排”翻转寻址算法。将“跨厂转移物流时间”视同标准工时处理，屏蔽物理空间差异。
    
  - **换型优化启发式算法**：在时间槽寻址时，实现“同属性任务优先连续排产”的启发式优化逻辑。当设备存在多个可排产任务时，优先选择与上一任务 `SetupAttribute` 相同的任务，减少换型次数，提升瓶颈设备产能。
    
  - **性能基准交付**：交付热点路径的 Profiler 测试报告，保障核心循环的 GC 零分配（Zero Allocation）及耗时达标。
    
  - **⚠️ V1.0 范围管控（不做的功能）**：
    
    - **不支持多资源协同约束**：V1.0 只考虑单一设备资源的时间槽寻址，不实现"机床+模具+操作工"的多资源交集运算。如需多资源限制，由 PMC 手动调整。
      
    - **不支持工序重叠（Overlapping）**：V1.0 默认上一道工序全部完成后，下一道才开工。不实现带 Offset 的时间重叠推演和 TransferBatchSize（最小转移批量）逻辑。
    
- **技术能力**：精通 C# 底层内存管理与 GC 机制；精通底层数据结构；熟练运用 `struct`、`ref` 语义与 `ObjectPool` 优化内存分配。
  
- **业务能力**：深刻理解车间时间轴、工序拓扑约束、换型时间（Setup Time）等物理排程概念。
  
- **⛔ 绝对红线**：
  
  - **严禁 I/O 操作**：排程计算代码内绝对禁止连接数据库或调用外部 API。
    
  - **严禁 LINQ**：在排程热点循环体内，绝对禁止使用引发隐式内存分配的语法。

## 🔴 边界 1：单据的"生死权"绝对归属 ERP，APS 拒绝凭空造单

### **易犯错误**

认为 APS 在 02:00 重排时，需要删掉未开工的单据，自己根据 BOM 重新算缺口并 `new` 出全新的虚拟单据。

### **物理真相**

本公司的所有顶层 MTO、中间库 MTS、厂间 MTS，均由 ERP 事先结合全局供需平衡和固定批量计算完毕，并作为物理实体下达。

### **架构红线**

1. **2号位在 02:00 拉取数据时，必须全量拉取 ERP 中所有"未完结（Open）"的订单实体。**
2. **APS 绝对没有权力销毁 ERP 下达的合法单据**（除非 ERP 发送了取消指令）。
3. **2号位的动作是：为这些真实存在的单据生成底层的排程工序（Task）。**

### **代码检查点**

```csharp
// ✅ 正确做法
var erpOrders = await _erpAdapter.GetAllOpenOrdersAsync(domainKey);
foreach (var order in erpOrders)
{
    // 为真实存在的ERP单据生成Task
    var tasks = await _taskGenerator.GenerateTasksFromOrder(order);
    context.Tasks.AddRange(tasks);
}

// ❌ 错误做法（严禁）
// 删除未开工的单据
var pendingOrders = context.Orders.Where(o => o.Status == "PENDING");
context.Orders.RemoveRange(pendingOrders);

// 根据BOM重新计算缺口并造单
var shortage = CalculateShortage();
var newOrder = new Order { /* 凭空造单 */ };
context.Orders.Add(newOrder);  // 严禁！
```

## 🔴 边界 2：Pegging 的本质是"红娘连线"，而非"算缺口"

### **易犯错误**

认为 Pegging 是为了算出还差多少料，从而触发系统去造新单。

### **物理真相**

所有单据都已存在，Pegging 的目的是将"顶层需求"与"底层供给"建立动态血缘关系，从而实现优先级的传导。

### **架构红线**

1. **5号位的 Pegging 逻辑，只负责在内存中通过指针将 Demand（需求）连向 Order/MTS（现成单据），绝对禁止越级连向 Task。**
2. **动态洗牌原则**：昨天连向客户 A 的中间 MTS，今天可能因为交期变化，被 5号位重新连向 VIP 客户 B。单据实体不变，只有"连线"在每天 02:00 被动态撕毁与重建。

### **代码检查点**

```csharp
// ✅ 正确做法：5号位返回Pegging连线凭证
public class PeggingVoucher
{
    public string DemandId { get; set; }        // 顶层需求ID
    public string SupplyOrderId { get; set; }   // 连向的现成单据ID（Order/MTS）
    public decimal AllocatedQuantity { get; set; }
}

// 2号位执行连线
foreach (var voucher in peggingVouchers)
{
    var demand = context.Demands.Find(voucher.DemandId);
    var supply = context.Orders.Find(voucher.SupplyOrderId);
    
    // 建立内存指针连线
    demand.PeggedToOrder = supply;
    supply.PeggedDemands.Add(demand);
}

// ❌ 错误做法（严禁）
// 计算缺口并造单
var shortage = demand.Quantity - existingSupply.Sum(s => s.Quantity);
if (shortage > 0)
{
    var newOrder = new Order { Quantity = shortage };  // 严禁！
    context.Orders.Add(newOrder);
}

// ❌ 错误做法（严禁）
// 越级连向Task
demand.PeggedToTask = task;  // 严禁！必须连向Order
```

## 🔴 边界 3："N波级联扫尾"确保全量覆盖，一个都不能少

### **易犯错误**

认为只有被顶层订单 Pegging 连线到的 MTS 才需要排产。

### **物理真相**

ERP 下达的某些 MTS 可能是纯粹的备货，暂时没有明确的上级需求，但车间依然必须执行。

### **架构红线**

1. **必须严格执行"N波供需翻转（孤儿扫尾）"机制。**
2. **第一波连线结束后，所有未被连线的"孤儿 MTS"必须按照低阶码（LLC）强制翻转为需求。**
3. **确保全公司所有的 MTS，哪怕是处于 BOM 最底层的备货，都必须生成 Task 并交由 1号位进行排产。**

### **代码检查点**

```csharp
// ✅ 正确做法：N波级联扫尾
// 第一波：顶层需求Pegging
var peggingVouchers = await _peggingRule.ExecuteFirstWavePegging(demands, orders);
ApplyPeggingVouchers(peggingVouchers);

// 第二波：孤儿MTS扫尾
var orphanOrders = context.Orders
    .Where(o => o.OrderType == "MTS")
    .Where(o => !o.PeggedDemands.Any())  // 未被连线的孤儿
    .OrderBy(o => o.Material.LowLevelCode);  // 按LLC排序

foreach (var orphan in orphanOrders)
{
    // 强制翻转为需求，继续Pegging
    var syntheticDemand = new Demand
    {
        SourceOrder = orphan,
        Quantity = orphan.Quantity,
        Priority = orphan.BaseScore  // 使用备货基础分
    };
    context.Demands.Add(syntheticDemand);
}

// 继续执行后续波次，直到所有单据都被覆盖
var nextWaveVouchers = await _peggingRule.ExecuteNextWavePegging(context);

// ❌ 错误做法（严禁）
// 只处理被连线的单据，忽略孤儿MTS
var ordersToSchedule = context.Orders.Where(o => o.PeggedDemands.Any());
// 这会导致备货MTS被遗漏！
```

## 🔴 边界 4："下发 MES"的唯一判定标准是"时间冻结区"

### **易犯错误**

认为只要 ERP 里有这个单据号（MTS NO），车间就应该看到，就算作已下发。

### **物理真相**

ERP 可能会下达未来半年的计划单据，如果全部推给车间，现场将彻底混乱。

### **架构红线**

1. **存在 MTS 单号 ≠ 车间可见 ≠ 已下发 MES。**
2. **唯一的下发阀门**：只有当 1号位将某个 Task 的排程时间安排进了"未来 3 天（或各域定义的冻结区天数）"内，5号位才会在落库前的一瞬间为其打上 `IsFrozen = true` 标签。
3. **只有带有 `IsFrozen = true` 标签的数据，才允许推送到 MES，真正成为车间的生产指令。**
4. **其他单据默默躺在数据库里，随时准备在次日 02:00 被 1号位重新调整时间。**

### **代码检查点**

```csharp
// ✅ 正确做法：5号位在落库前打标
public interface IFreezeZoneRule
{
    bool ShouldFreeze(Task task, DateTime currentTime, int freezeHorizonDays);
}

// 实现示例
public class DefaultFreezeZoneRule : IFreezeZoneRule
{
    public bool ShouldFreeze(Task task, DateTime currentTime, int freezeHorizonDays)
    {
        if (task.PlannedStartTime == null) return false;
        
        var freezeDeadline = currentTime.AddDays(freezeHorizonDays);
        return task.PlannedStartTime <= freezeDeadline;
    }
}

// 2号位在落库前调用5号位打标
foreach (var task in context.Tasks)
{
    var shouldFreeze = await _freezeZoneRule.ShouldFreeze(task, DateTime.Now, 3);
    task.IsFrozen = shouldFreeze;
}

// 3号位推送MES时严格过滤
var tasksToMES = await _dbContext.Task
    .Where(t => t.IsFrozen == true)  // 唯一阀门
    .Where(t => t.Status == "PENDING")
    .ToListAsync();

await _mesAdapter.PushTasksAsync(tasksToMES);

// ❌ 错误做法（严禁）
// 直接推送所有单据到MES
var allTasks = await _dbContext.Task.ToListAsync();
await _mesAdapter.PushTasksAsync(allTasks);  // 严禁！会导致车间混乱
```

## 🔴 边界 5：V1.0 剔除"不良品/报废"纠偏，坚守 1:1 刚性流转

### **易犯错误**

前工序计划 100个，报废 5个，APS 试图过于智能地将后工序待排数量篡改为 95个，甚至自动生成 5个的补料 Task。

### **物理真相**

异常损耗在现场极其多变（可能报废，可能稍后补齐）。过度智能的篡改会导致状态机极易崩溃。

### **架构红线**

1. **V1.0 坚决不考虑不良品带来的数量折算。**
2. **Task 的计划数量在上下游之间 1:1 刚性传递。**
3. **MES 报工作业产生的实际缺口，交由 ERP 在下一轮整体供需计算时下达新的 MTS 来弥补，APS 引擎内部严禁自作主张修改后续工序数量。**

### **代码检查点**

```csharp
// ✅ 正确做法：1:1 刚性传递
public void GenerateDownstreamTasks(Task upstreamTask, Routing routing)
{
    foreach (var operation in routing.Operations)
    {
        var downstreamTask = new Task
        {
            OrderNo = upstreamTask.OrderNo,
            OperationSeq = operation.Seq,
            PlannedQuantity = upstreamTask.PlannedQuantity,  // 1:1 刚性传递
            PreviousTask = upstreamTask
        };
        
        context.Tasks.Add(downstreamTask);
    }
}

// ❌ 错误做法（严禁）
// 根据报废数量调整后续工序
var scrapQuantity = upstreamTask.ScrapQuantity;
var downstreamTask = new Task
{
    PlannedQuantity = upstreamTask.PlannedQuantity - scrapQuantity  // 严禁！
};

// ❌ 错误做法（严禁）
// 自动生成补料Task
if (scrapQuantity > 0)
{
    var补料Task = new Task
    {
        PlannedQuantity = scrapQuantity,
        TaskType = "补料"  // 严禁！必须由ERP下达
    };
    context.Tasks.Add(补料Task);
}
```

## 🔴 边界 6：中间库 MTS 的批次拆分规则配置权归 PMC，5号位按规则动态执行

### **易犯错误**

认为 APS 应该"自作主张"将大批量的中间库 MTS（如 1000 件）拆分成多个小批次（如 4×250 件），而不考虑 PMC 的业务规则。

### **物理真相**

中间库 MTS 的固定批量往往设置得非常大（如 1000 件），但车间设备产能有限。如果一次性生产 1000 件，会长时间占用设备，影响下游 MTO 或其他 MTS 的交货。因此，需要根据**经济批量规则（MOQ/EOQ）**、设备负荷、交货压力等因素，将大批量 MTS 拆分成多个批次分散生产。

### **架构红线**

1. **拆批规则配置权归 PMC**：PMC 在系统中配置拆批规则（如最小批量 200 件、最大批量 500 件、瓶颈设备优先拆分等）。
2. **5号位按规则动态执行**：每天 02:00 排程时，5号位读取 PMC 配置的规则，根据当前设备负荷、下游交货压力等实时因素，动态下发《拆批凭证》。
3. **2号位统一执行拆批**：2号位根据凭证，将 ERP 单据拆分成多个逻辑块，为每个块生成独立的 Task 序列。
4. **只有中间库 MTS 允许拆分**：MTO 订单绝对禁止拆分（客户订单必须整单交付）。
5. **APS 绝对禁止自作主张**：5号位必须严格按照 PMC 配置的规则执行，不得擅自修改拆批逻辑。

### **典型场景**

```
场景：中间库 MTS 动态拆批

PMC 配置规则（一次性配置）：
- 最小经济批量（MOQ）：200 件
- 最大经济批量（EOQ）：500 件
- 瓶颈设备拆批策略：优先拆分
- 非瓶颈设备策略：尽量保持大批量

ERP 下达：
- MTS-2024001，物料：半成品A，数量：1000 件，固定批量：1000

每天 02:00 排程时，5号位动态执行：
- 读取 PMC 配置的规则（MOQ=200, EOQ=500）
- 检测当前设备负荷：85%（较高）
- 检测下游交货压力：有 2 个紧急 MTO 订单
- 裁决：将 1000 件拆分成 3 批次（400 + 400 + 200）
- 返回《拆批凭证》给 2号位

2号位执行：
- 根据凭证，将 MTS-2024001 拆分成 3 个逻辑块
- 为每个逻辑块生成独立的 Task 序列
- 继承原 MTS 的优先级分数（10 分）

1号位排程：
- 为 3 个批次独立排时间
- 可以插空排程，避免长时间占用设备
```

// ✅ 正确做法：5号位按 PMC 配置的规则动态拆批
public class TaskSplitVoucher
{
    public string OriginalOrderNo { get; set; }     // 原始 MTS 订单号
    public List<SplitBatch> Batches { get; set; }   // 拆批结果
    public string SplitReason { get; set; }         // 拆批理由（如：设备负荷85%，下游有紧急订单）
}

public class SplitBatch
{
    public int BatchSeq { get; set; }               // 批次序号（1, 2, 3）
    public decimal Quantity { get; set; }           // 批次数量（400, 400, 200）
    public int InheritedPriority { get; set; }      // 继承的优先级分数
}

// 5号位：按规则动态拆批
public class TaskSplitRule : ITaskSplitRule
{
    public TaskSplitVoucher Execute(Order mtsOrder, SplitRuleConfig config)
    {
        // 读取 PMC 配置的规则
        var moq = config.MinimumOrderQuantity;  // 200
        var eoq = config.EconomicOrderQuantity; // 500
        
        // 检测实时因素
        var deviceLoad = _deviceMonitor.GetCurrentLoad(mtsOrder.ResourceId);
        var downstreamPressure = _demandAnalyzer.GetDownstreamUrgency();
        
        // 动态裁决
        if (mtsOrder.Quantity <= eoq)
        {
            // 不拆分，保持原批量
            return new TaskSplitVoucher
            {
                OriginalOrderNo = mtsOrder.OrderNo,
                Batches = new List<SplitBatch>
                {
                    new SplitBatch { BatchSeq = 1, Quantity = mtsOrder.Quantity }
                }
            };
        }
        else
        {
            // 拆分成多个批次
            var batches = SplitByEOQ(mtsOrder.Quantity, moq, eoq);
            return new TaskSplitVoucher
            {
                OriginalOrderNo = mtsOrder.OrderNo,
                Batches = batches,
                SplitReason = $"设备负荷{deviceLoad}%，下游有{downstreamPressure}个紧急订单"
            };
        }
    }
}

// 2号位：根据凭证统一执行拆批
public async Task ProcessTaskSplitVoucher(TaskSplitVoucher voucher)
{
    var originalOrder = await _erpAdapter.GetMTSOrderAsync(voucher.OriginalOrderNo);
    
    foreach (var batch in voucher.Batches)
    {
        // 为每个逻辑块生成独立的 Task 序列
        var tasks = await _taskGenerator.GenerateTasksFromBatch(
            originalOrder, 
            batch.BatchSeq, 
            batch.Quantity
        );
        
        // 继承优先级分数
        foreach (var task in tasks)
        {
            task.OriginalOrderNo = originalOrder.OrderNo;
            task.BatchSeq = batch.BatchSeq;
            task.Priority = batch.InheritedPriority;
        }
        
        context.Tasks.AddRange(tasks);
    }
}

## 🎯 架构原则总结

### **核心原则**

1. **ERP 是单据的唯一来源**：APS 只负责排程，不负责造单。
2. **Pegging 是连线，不是算缺口**：动态洗牌，不触发造单。
3. **全量覆盖，一个不漏**：孤儿MTS必须通过N波扫尾强制排产。
4. **冻结区是MES阀门**：只有进入冻结区的Task才推送车间。
5. **1:1 刚性流转**：V1.0 不考虑报废纠偏，交由ERP处理。
6. **拆批规则配置权归PMC**：5号位按PMC配置的规则动态拆批，禁止硬编码逻辑。

### **违规处理**

- **发现违规代码**：立即停止开发，通知0号位评审。
- **设计阶段违规**：设计方案驳回，重新设计。
- **代码阶段违规**：代码必须重构，不得合并到主分支。

## 📝 附录：常见问题解答

### **Q1：如果 ERP 下达的单据数量明显不足，APS 难道不应该自动补单吗？**

**A1**：不应该。这是 ERP 的 MRP 职责。APS 只负责排程，不负责供需平衡。如果发现缺口，应该：
1. 通过告警通知 PMC
2. PMC 在 ERP 中手动或自动触发 MRP 重算
3. ERP 下达新的 MTS 单据
4. APS 在下一次 02:00 拉取时自动纳入排程

### **Q2：孤儿 MTS 如果一直没有上级需求，会不会永远不排产？**

**A2**：不会。孤儿 MTS 在第二波扫尾时会被强制翻转为需求，并按照其基础备货分数进行排产。确保所有 ERP 下达的单据都会被执行。

### **Q3：如果前工序报废了 10%，后工序难道还按原数量排吗？**

**A3**：是的。V1.0 坚持 1:1 刚性流转。实际缺口由 ERP 在下一轮 MRP 中下达补料单。这样做的好处是：
- 状态机简单稳定
- 责任边界清晰（APS 不越权）
- 避免 APS 和 ERP 的数据不一致

### **Q4：冻结区设置为 3 天，是否意味着 3 天后的计划都不准确？**

**A4**：不是。3 天后的计划依然准确，只是：
- 3 天内的计划：锁定推送 MES，车间执行
- 3 天外的计划：每天 02:00 动态调整，保持最优

这样既保证了车间的稳定性，又保持了计划的灵活性。

### **Q5：中间库 MTS 的固定批量很大（如 1000 件），APS 如何拆分成小批次？**

**A5**：批次拆分是一个需要综合判断的业务决策，涉及：
- 设备的最小/最大经济批量（MOQ/EOQ）
- 当前设备负荷情况
- 下游 MTO 的交货压力
- 车间的实际产能
- 物料的周转效率

**V1.0 实现方式**：
- **PMC 配置规则**：PMC 在系统中配置拆批规则（MOQ=200, EOQ=500, 瓶颈设备优先拆分等）
- **5号位动态执行**：每天 02:00 排程时，5号位读取规则，根据实时设备负荷和下游交货压力，动态下发《拆批凭证》
- **2号位统一执行**：2号位根据凭证，将 ERP 单据拆分成多个逻辑块，生成独立的 Task 序列
- **PMC 保留干预权**：PMC 可以在界面上查看拆批结果，必要时手动调整

**为什么不是"自作主张"**：
- 5号位严格按照 PMC 配置的规则执行，不是硬编码逻辑
- 拆批规则由 PMC 一次性配置，系统只负责执行
- PMC 随时可以修改规则或手动干预结果

**V2.0 可能增强**：增加更多智能因素（如物料周转率、历史生产效率等），进一步优化拆批决策。
