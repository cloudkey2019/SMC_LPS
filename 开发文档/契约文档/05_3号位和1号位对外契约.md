### 6.10.5 发布内容快照契约 ContentSnapshotJson（0号位 方案 A 裁决，2026-08-22）

> 依据：0号位 第三轮正式复审报告（`_a5741a7_Commit冻结版(1).md`）§5.2 / §7 / §9.1 / §9.3 裁决（**批准方案 A**）。
> 性质：冻结技术基线**最小修正**（已发布版本内容可重放的物理载体），不重新打开业务、不新增表/版本体系/主题专用列。
> 字段名可由开发统一命名，但**业务语义固定**如下；本契约先行（红线 #5），代码（实体/Repository/Provider/发布链）按此对齐。

#### 落点（DDL 由 2号位 按变更申请执行，红线 #6；3号位 不自行 ALTER）

- `RuleSetVersion.ContentSnapshotJson`：`NVARCHAR(MAX) NULL`，保存该版本发布时的完整规则内容
- `ParameterSetVersion.ContentSnapshotJson`：`NVARCHAR(MAX) NULL`，保存该版本发布时的完整参数内容
- 不新增 Snapshot 表 / 版本体系 / 主题专用列；`StrategyProfileVersion` 核心结构不变（仍仅组合 `RuleSetVersionId` + `ParameterSetVersionId`）
- 不新增 `ChangeReason` 等审计字段（用既有 `GovernanceAuditLog`，0号位 §9.2）

#### 内容归属

| 载体 | 承载子块 |
|---|---|
| `RuleSetVersion.ContentSnapshotJson` | DemandPriority（需求优先级）+ 后续属于 RuleSet 的其它冻结规则内容 |
| `ParameterSetVersion.ContentSnapshotJson` | Lock（锁定/需求保护）、Supply（供给）、Procurement（含 PlanningYield）、SolverStrategy、CandidateGuardrail、BatchPolicy（⑧ 批量策略，2026-10-07 裁决） |

#### 结构化子块（统一聚合载体，主题 JSON 退出正式持久化列）

原 `DemandPriorityJson / LockJson / SupplyJson / ProcurementJson` 主题 JSON **退出版本表正式持久化字段**（0号位 §7.3：不是删除业务内容，而是统一它们的版本化物理载体），改为 `ContentSnapshotJson` 内结构化子块保存。JSON 键名与 FrozenStrategySnapshot 六块一致：

```
ContentSnapshotJson = {
  "DemandPriority":   { ... },                    // RuleSet 侧
  "Lock":             { ... },                    // ParameterSet 侧
  "Supply":           { ... },
  "Procurement":      { ..., "PlanningYields": [ ... ] },
  "SolverStrategy":   { ... },                    // 真实来源（P0-02 收口，替代空对象）
  "CandidateGuardrail":{ ... },
  "BatchPolicy":      [ ... ]                    // ⑧ 批量策略规则数组（发布时从 TaskSplitRuleConfig 投影，fail-open）
}
```

#### BatchPolicy 子块（⑧ 批量策略，2026-10-07 裁决「本轮落码」）

> - **载体两级承接**：主题表 `TaskSplitRuleConfig`（直接生效物理表，非版本化 JSON，3号位 治理 CRUD + 生效区间）；
>   发布 ParameterSetVersion 时把 active + 生效区间内规则投影为 `BatchPolicyRuleSnapshot` 列表写入本子块，
>   1号位 经 `FrozenStrategySnapshot.BatchPolicy` 消费。
> - **正式匹配粒度**：MaterialId + ProductionDepartmentId（ProductionDepartmentId NULL = Material 级默认）。
> - **装载端不裁剪**（2026-10-08 方案 A 定案）：`SolverStrategySnapshot.BatchPolicies` 整块**全量透传、不做 Domain 裁剪**
>   （与⑤⑥同向；⑧ 含可空轴 ProductionDepartmentId，裁剪会误丢 Material 级默认行）——按本域 MaterialId/ProductionDepartmentId
>   匹配由 1号位 消费侧（`PhaseOneConstraintBuilder` → `ConstraintContext.ExecutionBatchPolicies`）决定；域外规则不命中非错误。
>   Projection 接线：`FrozenStrategySnapshot.BatchPolicy` → `SolverStrategySnapshot.BatchPolicies`（2号位 `PeggingOrchestrator` 投影）。
> - **装载 fail-open**：缺子块/为空/损坏 → 空列表（无批量策略规则）；「缺策略 fail-closed（BATCH_POLICY_MISSING）」
>   属 1号位 消费侧信号，本子块不承载信号位。
> - **兼容字段不投快照**：ResourceGroupId / MinimumOrderQuantity / EconomicOrderQuantity 仅历史兼容，不参与 V1 正式匹配、不进本子块。

#### 生命周期语义（一次收口，0号位 §7）

- **发布阶段**（§7.1）：从主题维护对象装配各块 → **全部校验**（含 `SolverStrategyValidator` / `CandidateGuardrailValidator`）→ 聚合形成 `ContentSnapshotJson` → 写入 → 状态转 PUBLISHED
- PUBLISHED 后内容**不可原地修改**（历史不可覆盖，与"已 PUBLISHED 不可再次发布"一致）
- **Run 装载阶段**（§7.2）：`StrategyProfileVersionId` → `RuleSetVersion.ContentSnapshotJson` + `ParameterSetVersion.ContentSnapshotJson` → 反序列化六块 → FrozenStrategySnapshot；**缺失/损坏一律失败**（六块统一，P0-02）
- 2号位 一次 Run 装载一次；1号位 消费 Solver Strategy

#### 校验器接线（P0-02）

发布 ParameterSetVersion 前：`ValidateParameterSetVersionForPublishAsync` 反序列化 SolverStrategy/CandidateGuardrail 子块 → 调 `SolverStrategyValidator` / `CandidateGuardrailValidator` → 错误进 `result.Errors`，拒绝发布（接线路径见《P0-02执行蓝图》§四.5）。

### 6.11.1 IRunLifecycleService（运行生命周期服务）

### 6.11.3 ExpectedDomainKeysJson 语义（冻结规则）

- 存储：`ScheduleRun.ExpectedDomainKeysJson`（NVARCHAR(MAX)，JSON 数组，DDL CHECK `ISJSON=1` 约束）
- 冻结时机：Run 启动时一次写入，创建后**不可修改**；不得根据已创建 PlanVersion 反推（DDL 表头注释）
- 终态判定权威：ScheduleRun 终态（COMPLETED / PARTIAL_SUCCESS / FAILED）判定唯一依据该字段
- 数量规则：FULL ≥1 Domain；Candidate（RESCHEDULE）恰 1 Domain
- 去重规则（P1-01）：FULL 场景预期 Domain 集合**不可重复**（重复 DomainKey 一律拒绝）
- 校验失败 → 抛 `InvalidOperationException`（配置错误），**不静默降级**

### 6.11.4 Candidate 最小确认语义

- 确认落点：**仅审计**（`OperationType=ConfirmCandidate`，`EntityType=PlanVersion`，`EntityId`=被确认的 PlanVersion.Id）；`CandidatePlanVersionId` = 被确认的 PlanVersion.Id，记入 `Remarks`
- 仅记录：Actor / ConfirmedAt / CandidatePlanVersionId / 必要 Remark（经 `IGovernanceAuditLogRepository`；审计实体无独立列，`CandidatePlanVersionId` 记入 `Remarks`）
- **确认不写 `ActivatedAt` / `ActivatedBy`、不转 ACTIVE、不预检同域 ACTIVE**（二轮复审 P0-05 / P0-06：确认仅是记录动作，Base ACTIVE 存在不影响确认）
- 不强制 OA；不建 MultiDomain Candidate（每 Domain 仅确认其自身）
- 激活前置（二轮复审 P0-03 / P0-04 / P0-06 收紧）：
  - `DomainKey` 非空（V1 必填）
  - **已完成最小人工确认**：存在针对该 PlanVersion 的 `ConfirmCandidate` 审计记录
  - **来源 Run 可激活**：`SourceScheduleRunId` 非空，且其 `RunType != "INSERT_ORDER_WHATIF"`
  - **原子替换**：单事务内归档同域既有 ACTIVE（→ARCHIVED + ArchivedAt）再置本 Candidate 为 ACTIVE；`UQ_PlanVersion_OneActivePerDomain` 红线保留
