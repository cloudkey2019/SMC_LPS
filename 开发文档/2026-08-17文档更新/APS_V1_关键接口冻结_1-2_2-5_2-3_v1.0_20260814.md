# APS V1 关键接口冻结说明：1↔2、2↔5、2↔3

**版本**：v1.0  
**日期**：2026-08-14  
**状态**：开发接口冻结  
**目的**：让2号位可以继续增量开发，同时避免1、3、5号位后续各自实现时重新改变主链。

---

# 一、总原则

本文件只冻结**跨号位交接边界**，不重新设计各号位内部实现。

- 2号位仍是APS主流程和Pegging核心Owner；
- 1号位只拥有有限产能物理排程算法；
- 3号位只治理规则、参数、策略版本和运行生命周期边界；
- 5号位只提供复杂业务事实，特别是PI Position和跨厂/采购相关派生事实；
- 下游不得要求上游直接暴露源系统内部字段；
- 不使用逐笔远程调用模式，夜间以批量/内存Context交接为主。

---

# 二、1↔2接口冻结

## 2.1 责任边界

### 2号位负责

- 完成Demand排序和Pegging；
- DemandBalance / SupplyBalance；
- Allocation；
- Lock；
- PI Position消费；
- 计划良率数量反算；
- 形成LogicalProductionDemand；
- 准备Routing/Resource/Calendar/Material Quantity-Time/Execution约束；
- 调用1号位；
- 校验并持久化1号位结果。

### 1号位负责

- FinalTask生成；
- Resource选择；
- Start/End；
- 有限产能；
- Forward/Backward/Mixed；
- 拆批/合批；
- Setup邻接；
- Stage overlap/transfer batch；
- Candidate局部传播与同Domain兜底；
- FinalTask物理依赖；
- Explanation事实；
- Unscheduled/Unfulfilled结果。

---

## 2.2 调用入口

优先保留现有：

```csharp
IFiniteCapacityScheduler.SolveAsync(DomainSolveRequest request, CancellationToken ct)
```

不新建第二套Solver接口。

---

## 2.3 `DomainSolveRequest`冻结的九类输入

1. **RunBoundary**
   - ScheduleRunId
   - PlanVersionId
   - DomainKey
   - DataCutoffTime
   - HorizonStart/End

2. **LogicalProductionDemands**
   - AllocationSequence
   - DemandKey / OrderId
   - MaterialId / FactoryId
   - StartStageCode
   - NetOutputQty
   - PlannedProcessQty
   - RequiredAvailableTime
   - DemandSequence
   - PI No（可空）
   - IsUnlocated

3. **AllocationLineage**
   - AllocationSequence
   - DemandKey
   - SupplyKey/Type
   - Qty
   - AvailableTime

4. **RoutingNetwork**
   - RoutingOperation
   - RoutingDependency
   - 合法Path

5. **ResourceContext**
   - Eligibility
   - Capability
   - Calendar
   - Setup必要事实

6. **MaterialConstraints**
   - Material Quantity-Time Slice
   - 上游/跨Domain/跨厂AvailableTime

7. **StrategySnapshot**
   - 本次Run冻结的3号位策略/参数

8. **ImmovableFacts**
   - Execution
   - Firm
   - Frozen
   - Demand Protection对应的物理约束

9. **CandidateContext（仅Candidate）**
   - Base相关稳定锚点
   - 变化Seed
   - 外Domain ACTIVE共享资源阻挡块

---

## 2.4 `DomainSolveResult`冻结输出

至少包含：

- FinalTasks
- AllocationTaskShares
- TaskDependencies
- ScheduleExplanationFacts
- UnscheduledItems
- Evaluation/KPI摘要

### 红线

- 2号位不得收到结果后重新改变Resource/Start/End；
- 2号位不得在Solver前生成FinalTask；
- 1号位不得写数据库；
- 1号位不得重新做Demand排序或Pegging。

# 三、2↔5接口冻结

## 3.1 5号位定位

5号位是复杂事实计算方，不是Pegging插件中心。

主要负责：

- PI Position；
- BOM入口/Stage相关复杂事实；
- 跨厂模式和相关来源事实；
- Procurement/VMI/Received/Transit的ODS标准化事实；
- 其它确实需要源系统复杂业务知识的派生。

不负责：

- 最终Demand排序；
- Supply选择顺序执行；
- Allocation；
- Demand Protection最终扣减；
- Task；
- Solver；
- ScheduleRun；
- Explanation最终原因裁决。

---

## 3.2 PI Position接口

建议批量接口语义：

```csharp
Task<IReadOnlyList<ProductionInstructionPositionResult>>
CalculateProductionInstructionPositionsAsync(
    IReadOnlyList<ProductionInstructionPositionInput> inputs,
    FrozenFactParameters parameters,
    CancellationToken ct);
```

### Input至少包含

- ProductionInstructionNo
- MaterialId
- FactoryId
- ERP RemainingQty
- StageProgress
- OperationProgress（必要时）
- PI级Inventory
- XC
- PI级InterplantTransit
- Routing/StagePath
- Received / Strong Evidence
- 本次冻结相关参数

### Result至少包含

- ProductionInstructionNo
- TotalRemainingQty
- PositionType
- StageCode/LocationKey
- PositionQty
- AvailableTime（适用时）
- IsStrongEvidence
- IsUnlocated
- Issues

### 硬闭合

对每个PI：

> Σ PositionQty = ERP RemainingQty

### 红线

- 5号位不修改ERP/MES源事实；
- 5号位不决定该PI最终分给哪个Demand；
- 5号位不为同一物理份额返回多个可消费Position；
- 2号位先选PI，再消费该PI Position；
- PI Position异常可以降级UNLOCATED，但数量不闭合属于Domain失败级问题。

---

## 3.3 Procurement / Timed Supply接口边界

5号位负责尽量把源事实标准化成：

- SupplyType
- PhysicalSourceKey
- Material
- ReceivingFactory/Warehouse
- RemainingQty
- ETA
- AvailableTime
- Commitment/Confidence
- SourceDocument
- SourceUpdatedAt

ETA优先级和仓库可用偏移尽量在ODS/复杂事实层完成。

2号位负责：

- 按冻结Supply顺序消费；
- RemainingQty扣减；
- Allocation；
- Planning-only Placeholder缺口补位。

Planning-only Placeholder不是5号位正式源事实，不要求5号位落表。

---

# 四、2↔3接口冻结

## 4.1 3号位输出给2号位的不是“逐笔规则结果”

3号位负责治理：

- RuleSetVersion
- ParameterSetVersion
- StrategyProfileVersion

一次Run启动后形成冻结Snapshot。

2号位一次性装载并在内存执行。

禁止：

> 每分配一笔Demand就RPC调用3号位问“该怎么排”。

---

## 4.2 冻结Snapshot最小内容

### Demand排序

- Priority Segment定义
- First-match条件
- Segment内部排序字段及方向
- 稳定Tie-break规则

### Supply/Lock

- InventoryAvailabilityRule
- Demand Protection触发参数
- PI简单排序参数
- Procurement默认LT及相关参数

### Solver策略

- Forward/Backward/Mixed策略选择
- 动态瓶颈参数/Override
- On-time目标阈值
- Setup / Split / overlap等必要参数
- Candidate技术Guardrail

---

## 4.3 生命周期边界

3号位可负责：

- Run元数据创建/治理；
- ExpectedDomainKeysJson冻结；
- StrategyProfileVersion绑定；
- Candidate最小人工确认/激活边界。

2号位负责：

- 主流程实际执行；
- 每Domain计算；
- 结果持久化；
- Run结果状态回填/汇总协作。

### 不强制的内容

不要求为了文档统一强改：

- ScheduleRun具体在00:38还是其它分钟创建；
- PlanVersion壳具体在哪一步创建。

只要求：

- 关系可追溯；
- DataCutoffTime一致；
- ExpectedDomainKeysJson冻结；
- 状态终态闭合。

# 五、三个接口共同错误处理规范

## 5.1 可降级

- 单条PI Position非关键字段缺失，可UNLOCATED；
- 单条数据质量Issue可登记Issue/Explanation；
- Candidate个别替代资源不可用可继续搜索。

## 5.2 必须使Domain失败

- Demand/Supply数量不闭合；
- 同一物理Supply重复消费；
- Allocation事务无法闭合；
- FinalTask结果违反硬资源互斥；
- Solver返回数量丢失；
- PI Position总量无法与ERP RemainingQty闭合且无法保守定位；
- 关键数据库持久化事务失败。

## 5.3 不是运行失败

- 订单延期；
- 资源不足导致无法按期；
- 缺料导致最早日期变晚；
- 只能依赖ESTIMATED采购占位。

这些是业务结果，应返回Explanation/Unscheduled/Risk，不把ScheduleRun技术状态误置FAILED。

---

# 六、接口冻结后的并行开发规则

2号位现在可以继续开发：

- Demand/Supply Balance
- Allocation
- LogicalProductionDemand
- Transaction
- Candidate
- Persist层

不必等待1/3/5全部完成。

### 占位策略

- 1号位未完成：使用符合最终Request/Result契约的Stub；
- 5号位未完成：使用固定测试PI Position Fact Fixture；
- 3号位未完成：使用固定冻结StrategySnapshot Fixture。

这些Fixture只能用于联调，不得发展成正式第二套实现。

---

# 七、变更控制

从本接口冻结后：

- 某号位认为字段不足，先证明现有冻结业务无法表达；
- 优先追加DTO字段，不优先新增物理表；
- 不允许某号位单方面改变上下游职责；
- 不允许用“代码已经这么写了”要求其它号位接受旧主链；
- 真正需要改变业务时，必须显式提出重新打开对应冻结决策。
