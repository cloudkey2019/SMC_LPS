# APS V1 20260901 职责、前端接口与权限归属调整正式裁决

**版本**：v1.0  
**日期**：2026-09-01（北京时间）  
**裁决人**：0号位  
**适用范围**：APS V1  
**文档性质**：技术职责与跨号位接口调整的正式裁决文件  
**上位约束**：本裁决不得改变既有APS V1冻结业务流程、Pegging业务、有限产能业务、Candidate业务、PlanVersion业务、Manual ETA业务语义及各类数量/时间闭环；仅调整技术职责、接口接入层、认证权限归属和数据库Owner边界。

---

# 一、裁决目的

2026-08-31项目组重新讨论4号位前端与各后端号位的交互方式，并确认：

1. 2号位继续承担APS排程主流程与Pegging核心业务，但不再直接对4号位提供HTTP/API；
2. 3号位集中承担规则、参数、策略、认证、角色权限及运行治理；
3. 5号位在原复杂业务事实职责基础上，新增面向4号位的非治理类APS业务接口接入/中转职责；
4. 4号位正式只与3号位、5号位进行前端API交互；
5. 原2号位已有认证代码整体移交3号位；
6. V1权限必须同时支持功能权限和业务范围权限；
7. 数据库结构归属按业务Owner划分，不再使用“所有DDL统一由2号位执行”的泛化规则。

本裁决只对上述技术职责和接口结构进行更新。

---

# 二、不得改变的既有冻结业务

本次调整不得重新打开以下已冻结内容：

- 2号位仍是排程主流程、Pegging、Demand/Supply、DemandBalance、SupplyBalance、Allocation、Lock、CrossFactory、AvailableTime、Demand Protection、LogicalProductionDemand、结果校验与持久化Owner；
- 1号位仍是唯一有限产能求解器（Solver）Owner；
- 3号位仍负责规则、参数、策略版本和ScheduleRun/Candidate治理边界；
- 5号位仍负责复杂外部/业务事实，包括PI Position、采购/VMI、跨厂、MES等事实；
- Manual ETA仍为APS人工事实，由5号位维护事实/API，2号位计算Effective ETA和最终AvailableTime；
- 白天Candidate严格单Domain；
- CTP/插单影响分析可形成WHATIF候选版本，但不可激活为ACTIVE；
- 需求保护（Demand Protection）的实际保护数量、创建、消费、释放仍属于2号位；
- 4号位不直接写运行数据库；
- 4号位不直接调用1号位。

---

# 三、4号位新的统一前端接口边界

## 3.1 正式原则

> **4号位只允许直接调用3号位和5号位对外API。**

不再存在正式的：

```text
4号位 → 2号位 HTTP/API
```

也不存在：

```text
4号位 → 1号位
```

## 3.2 两条前端通道

### A. 治理、安全、运行治理类：4号位 → 3号位

包括：

- 登录/刷新/登出/当前用户；
- 用户/角色/权限；
- 功能权限；
- 业务范围权限；
- RuleSet / ParameterSet / StrategyProfile；
- Demand Priority配置；
- Diff/发布/退役/校验；
- 白天Candidate Run创建；
- CTP/插单试算发起；
- LOCAL_RESCHEDULE发起；
- MANUAL_RESCHEDULE发起；
- Candidate确认/激活；
- FAILED恢复治理。

### B. 非治理类APS业务与复杂事实类：4号位 → 5号位

包括：

- Overview；
- Order/需求计划；
- Gantt/资源计划；
- Explanation；
- Supply/Pegging追溯；
- PI Position；
- Manual ETA；
- Demand Protection查看；
- Demand Protection释放中转；
- MES资格/受控操作中转；
- 其它面向4号位的APS业务查询/操作中转。

---

# 四、2号位职责保持，但退出前端HTTP层

2号位继续负责排程主流程、Demand/Supply、Pegging、DemandBalance/SupplyBalance、Allocation、Lock、CrossFactory、AvailableTime、Demand Protection、LogicalProductionDemand、调用1号位、结果校验与持久化。

从本裁决生效后：

> **2号位不再承担4号位前端HTTP Controller/API职责。**

2号位向内部调用方提供稳定的Application Service、Query Service、Domain Service及必要Contract/DTO。

---

# 五、5号位新增“业务接口接入/中转层”职责

5号位新增：

- 面向4号位的非治理类HTTP Controller；
- 前端查询DTO；
- 页面需要的只读聚合；
- Token/权限上下文接入；
- 调用2号位Query/Application Service；
- 受控写操作中转；
- 将2号位服务结果转换为4号位稳定契约。

> **中转权不等于业务所有权。**

5号位不得重做Pegging、Demand/Supply Balance、Allocation、Demand Protection、CrossFactory、最终AvailableTime、排程主流程，也不得直接修改2号位核心运行结果或建设第二套运行事实。

---

# 六、3号位完整接管认证与权限

原2号位已有认证代码整体移交3号位。

3号位完整负责：

- APS_Auth数据库；
- Login / Refresh / Logout / Current User；
- User / Role / Permission；
- UserRole / RolePermission；
- 功能权限判断；
- 业务范围权限；
- 权限审计；
- 认证/授权相关Repository、Service、Controller和DDL。

原“认证继续归2号位、3号位只增量实现RBAC”的旧方案废止。

---

# 七、V1权限正式范围

## 7.1 功能权限：V1必须实现

至少覆盖查看计划、CTP、插单影响分析、局部重排、人工重排、Candidate确认、规则/参数维护、规则发布、Manual ETA维护、Demand Protection释放、MES受控操作、用户/角色/权限管理、审计查看。

## 7.2 业务范围权限：V1必须实现

至少支持：

- 工厂（Factory）
- 产品族（ProductFamily）
- 部门/生产部门（Department / ProductionDepartment）
- 计划域（Domain）

并允许组合，例如：
- 只能看天津工厂 + 产品族X；
- 能看北京/天津但只能看机加部门；
- 只能维护指定产品族；
- 只能确认指定Domain。

## 7.3 V1不要求

不建设任意记录级权限、任意字段级权限、单条订单/Task逐条授权、字段脱敏权限平台、通用ABAC/DSL权限引擎。

---

# 八、权限执行边界

权限不能只靠4号位前端隐藏按钮。

正式执行链：

```text
3号位：认证 + 角色 + 功能权限 + 业务范围
        ↓
4号位：菜单/页面/按钮展示
        ↓
3号位或5号位API：后端再次鉴权
```

5号位业务接口需读取3号位签发/提供的身份与权限上下文，校验功能权限与Factory/ProductFamily/Department/Domain范围，再调用2号位Query/Application Service。

2号位不维护“谁拥有什么权限”的规则，只消费已经校验并限定后的业务Scope。

---

# 九、数据库结构Owner原则调整

旧的“所有数据库DDL都必须由2号位执行”的泛化理解废止。

正式原则：

> **数据库结构由业务Owner负责；涉及其它Owner核心业务表时再走跨号位评审。**

- 2号位：Pegging、Demand/Supply Balance、Allocation、PlanVersion、ScheduleRun运行结果、FinalTask持久化、APS核心运行事实；
- 3号位：Rule/Parameter/Strategy治理结构、APS_Auth、用户/角色/权限、业务范围权限、权限审计；
- 5号位：ODS/复杂事实自属结构、PI Position相关事实、ProcurementManualEtaOverride及5号位自属事实结构。

5号位不得为了中转前端请求新建第二套2号位运行表。

---

# 十、G4 / G7 / G8 / Schedule查询归属调整

此前3号位只读封装的G4（Run列表）、G7（Domain依赖）、G8（Domain状态）及Schedule查询，为避免长期形成“部分业务结果找3号位、其它业务结果找5号位”的例外，正式调整为：

> **逐步移交5号位业务接口接入层。**

要求：

- 尽可能保持已有URL和DTO兼容；
- 如需改契约，必须先修改《APS_集成接口设计》；
- 3号位不再新增同类查询接口；
- 5号位读取2号位事实或调用2号位Query Service，不自行重算；
- 不新增中转表。

---

# 十一、关键接口冻结文档处理

现有《APS V1关键接口冻结说明：1↔2、2↔5、2↔3》和《APS V1关键接口冻结补充说明 Manual ETA / SupplyFact》仍包含大量有效接口细节。

为避免长期存在“集成接口设计 + 关键接口冻结 + 补充冻结”三套接口基线：

> **新版《APS_集成接口设计》完整吸收其仍有效内容后，上述两份关键接口冻结文档正式废止为历史追溯文档。**

废止生效条件：

1. 新版集成接口完整继承1↔2、2↔5、2↔3有效冻结内容；
2. 完整继承Manual ETA / SupplyFact语义；
3. 新增本次4↔3、4↔5、3↔2、5↔2边界；
4. 经0号位确认无业务漂移；
5. 当前有效基线索引同步更新。

---

# 十二、权限与审批旧文档处理原则

《APS 权限与审批设计方案 v1.0》《APS 权限与审批系统实施方案 v1.0》保留RBAC、业务范围控制、审计、独立APS_Auth、不做复杂ABAC、权限不能只靠前端等有效方向，但需按当前冻结基线修正：

- 认证/权限Owner改为3号位；
- 业务范围至少为Factory、ProductFamily、Department/ProductionDepartment、Domain；
- 不把任意记录级/字段级权限纳入V1；
- 旧审批场景不得反向覆盖当前APS V1冻结业务；
- 不新增PAUSE/RESUME闭环；
- 审批是否V1必做及具体场景必须服从当前最终业务冻结，而不能直接沿用2026年3月旧方案。

---

# 十三、文档修改顺序

本裁决发布后：

1. 《APS_集成接口设计》升版，完整继承旧内容，仅加入本次调整；
2. 《APS 权限与审批设计方案》升版；
3. 《APS 权限与审批系统实施方案》升版；
4. 更新3号位实施包；
5. 更新4号位实施包；
6. 更新5号位实施包；
7. 2号位实施包做最小职责更新；
8. 《APS_数据架构与防腐层设计方案》只同步职责/接口层/数据库Owner变化；
9. 当前有效冻结基线索引更新；
10. 新版集成接口确认完整后，将两份关键接口冻结说明登记为历史废止。

数据库字段说明/DDL不因本裁决自动修改；待3号位完成认证权限实际结构设计并审核后，再按真实需要升版。

---

# 十四、最终裁决

> **4号位正式只面对3号位和5号位。**

> **3号位负责规则、参数、策略、认证、角色、功能权限、Factory/ProductFamily/Department/Domain业务范围权限以及运行治理。**

> **5号位负责复杂事实，并新增非治理类APS业务接口接入/中转职责。**

> **2号位仍拥有APS主流程和排程核心业务，但不直接面向4号位HTTP/API。**

> **1号位仍只负责有限产能Solver。**

> **业务接口中转不改变业务Owner。**

> **数据库结构按业务Owner负责，不再将所有DDL泛化归2号位。**

> **新版《APS_集成接口设计》发布并完整吸收旧关键接口冻结内容后，原关键接口冻结及其Manual ETA补充说明正式废止，只保留历史追溯。**
