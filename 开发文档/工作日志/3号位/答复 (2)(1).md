## 最终结论：当前不通过

本轮为：

* **P0：4项**
* **P1：7项**
* **P2：3项**

不过结论不是“3号位做坏了需要重写”。相反，规则/参数/策略治理、排程域定义（DomainDefinition）、候选计划（Candidate）合法性、失败恢复新建运行（ScheduleRun）、认证（Authentication）、基于角色的访问控制（RBAC）、业务范围（Business Scope）等主体骨架已经形成，应该保护。

真正卡住验收的是四个P0。

**第一，Auth代码和当前冻结 Auth DDL v1.1 已经物理不兼容。** 当前代码 `User` 使用 `UserCode/UserName/Status/RefreshToken/LockoutEnd/...` 等字段，`Permission` 使用 `Category/IsActive` 等字段，`AuthDbContext` 还注册了第14张 `GovernanceAuditLog`；而当前冻结DDL仍是 `LoginName/DisplayName/IsEnabled/...` 的13表结构。([GitHub][2]) 

而且还有一个非常硬的冲突：当前代码13个权限码是 `plan.view`、`candidate.confirm`、`rule.maintain` 等，没有 `aps.` 前缀；但冻结 DDL 的 `PermissionCode` 有 `LIKE 'aps.%'` 约束。当前代码和当前冻结DDL放在一起，权限种子本身就不能正常成为一套一致系统。([GitHub][3]) 

**第二，高风险治理写接口没有完整功能权限。** 例如排程域定义（DomainDefinition）的新建、修改、启停，白天 Candidate Run 创建、FAILED恢复等接口目前没有对应功能权限 Policy；全局 FallbackPolicy 只保证“已经登录”，不能证明“有权做这件事”。([GitHub][4]) 当前已有的功能权限处理器本身方向没问题，但它只检查 PermissionCode。([GitHub][5])

**第三，业务范围（Business Scope）没有真正进入3号位治理写接口。** 代码已经正确实现了 `UserDataScope + RoleDataScope → DataScopePolicy` 的有效范围模型，这部分我判定通过；但 `GovernanceController` 的写操作没有真正消费这个 Scope。因此，一个只有 `Domain=D01` 权限的人，只要具有 CandidateConfirm 功能权限，目前看不到后端硬校验阻止他去确认或激活 D02。([GitHub][6]) 这直接不符合3号位实施包已经冻结的“D01用户不能确认D02 Candidate”等验收要求。

**第四，第14张 `GovernanceAuditLog` 不能因为代码已经写了，就自动成为冻结表。** 当前冻结 Auth v1.1 明确是在原13张表上增量对齐，而且已有正式 `AuditLog`；但现在代码另外建了一套 GovernanceAuditLog，并且 Candidate确认写到这里，Candidate激活还反过来依赖这张表证明“已经确认”。([GitHub][7]) 这已经不只是“DDL漏了一张表”，而是代码自行形成了第二套审计真相。

### 你上传的3号位AI派单，我的正式答复

它发现“**Auth代码、DDL、当前测试库发生漂移**”这一点是对的。 但它后面的推理我**不同意原样批准**。

它把“F-G5代码侧真源”扩大解释成：

> 整个 Auth Schema 都以当前代码为最高真源，代码里有什么字段就写进 v1.2 DDL。

这个结论过头了。当前能核到的 F-G5 是 RBAC实现和权限码播种相关；我没有在当前项目来源里找到一份更高优先级正式裁决，明确说“User/Role/Permission/AuditLog整个物理Schema以后无条件以当前代码覆盖冻结文档”。而最新冻结文档仍明确：APS_Auth、DDL、Migration、升级脚本都归3号位Owner，但实现仍应服从冻结业务。

而且派单本身有一个事实错误：它说 **Permission DDL没有 `Module`**，实际上当前 v1.1 DDL明确有 `Module`。真正的差异是 DDL 有 `ActionType`，代码变成了 `Category + IsActive + UpdatedAt`。

所以我对 R1、R2 的正式拍板是：

> **R1：A′，不是原A，也不是B。**
> 同意3号位立即产出 **Auth DDL v1.2冻结对齐版**，但不是“照抄当前代码”。应以**最新冻结业务 + 已明确需要保护的现有Auth能力**共同收口。Refresh、锁定、登录失败次数等合理现有能力可以保留；`User.FactoryId/DepartmentId`不能成为第二套业务范围真值；权限码前缀、字段名称必须一次统一。
>
> **R2：A。** 当前开发/测试阶段，在 **v1.2先冻结以后**，直接重建 APS_Auth 最简单、风险最低，不需要为测试数据维护复杂ALTER链。
>
> **GovernanceAuditLog：不同意作为第14张正式表并入v1.2。** 优先把规则治理、Candidate确认、RBAC变更统一收到现有 `AuditLog`。也**不需要找2号位回来补脚本**，因为9月1日以后APS_Auth DDL/Migration本来就已经完整归3号位。

另外几个P1也比较重要：`/api/Auth/me` 目前只返回用户、角色和权限，没有返回 Factory/ProductFamily/Department/Domain Scope；([GitHub][8]) Candidate Run虽然壳已经创建得不错，但代码自己还写着“3→2触发接缝本轮未接线”，而这件事在最新接口和2号位实施包里其实已经冻结，不再是待裁决项。([GitHub][7])  此外，很多审计 Actor 仍由请求中的 `PublishedBy/Actor/OperatedBy` 提供，而不是真正从JWT取当前用户，也需要整改。
