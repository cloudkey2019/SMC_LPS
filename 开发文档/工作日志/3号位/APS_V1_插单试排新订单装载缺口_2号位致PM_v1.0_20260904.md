## 一、结论一句话

白天候选排程的 `INSERT_ORDER_WHATIF`（插单试排 / CTP / 插入影响分析）**在需求源头就是缺口**：3号位 的需求只覆盖到「以当前 ACTIVE 为只读基线、在基线上算一版候选」（字面 = 重排基线那套订单），**没有「新订单从哪来、怎么进候选」的字段与机制**。这个裂缝在源头不在实现，2号位 不写代码，请 PM 先拍板。

---

## 二、背景：两种白天候选，语义不同

3号位 的白天候选接口（`POST api/Governance/run/candidate`）的 `ScheduleRun.RunType` 有：

| RunType | 业务语义 | 需求覆盖情况 |
|---|---|---|
| `MANUAL_RESCHEDULE` | 手动重排（基线订单换规则/换参数重算一版） | ✅ 3号位 需求覆盖（重排基线） |
| `LOCAL_RESCHEDULE` | 本地重排（局部调整） | ✅ 3号位 需求覆盖 |
| `INSERT_ORDER_WHATIF` | **插单试排**：模拟「新插一笔订单」对产能/交期的影响（CTP / 插入影响分析） | ⛔ **需求未覆盖**（无新订单入口） |

冻结的「用途×运行类型」合法组合里，`插入订单预演 + CTP`、`插入订单预演 + 插入影响分析` 明确存在，且**永远只查看、不可采用**——但「插入的订单」这个输入在整条链上没有任何字段承接。

---

## 三、缺口定位（证据）

1. **3号位 需求正文只到「在基线上算一版候选」**：`§一` 原则 =「以当前生效计划为只读基线，不修改基线，在基线上算一版候选」；`§2.2` 建候选壳时 `PlanHorizonStart/End` 直接**复制基线计划窗口**，无任何「新订单」相关列或入参。
2. **候选壳无订单**：2号位 回执事项四「以创建时冻结的 `BasePlanVersionId` 为准」——本质是**借基线那套订单**填候选的需求集，对 `MANUAL_RESCHEDULE` 成立，对 `INSERT_ORDER_WHATIF` 不成立（插单试排恰恰要的是「基线订单 + 一张新单」，不是「纯基线」）。
3. **结论**：「在基线上算一版候选」与「插单试排」两个语义没对上，裂缝在**源头契约**，不在 2号位 实现。

## 四、核心一问 + 草拟方案

### 核心一问：白天候选要不要吃「白天新同步的订单」？

- **不要** → `INSERT_ORDER_WHATIF` 短期只做「纯基线重排」，插单语义后置，请 PM 在冻结文档里注明 V1 暂不支持。
- **要** → 需要三件事落地（见下）。

### 若要，三件事

1. **新订单从哪来（二选一，请 PM 定口径）**
   - **口径 A**：3号位 在创建候选时传 `OrderNos` 列表（显式、可控、可审计，推荐）；
   - **口径 B**：自动吃 `Order_Canonical` 里基线没有的 delta（增量自动发现，无需传参，但依赖同步时点）。

2. **2号位 装载新单**：复用 `OrderLoadingService`（`sp_SyncOrdersToPartitionTable`，`Order_Canonical → Order 分区表`）按**候选 PlanVersionId** 装新单；需求集 = **基线订单 ∪ 候选新单**。此路径已存在，只需定「按候选 VersionId 装」的口径。

3. **契约联动**：3号位 改 `CandidateRunCreateSpec`（创建入参）加新订单字段 + 校验（口径 A 加 `OrderNos`；口径 B 加同步时点），并同步建壳/审计动作。

### 连带两问（请 PM 一并定）

- **Q1 新订单 BOM 白天不齐谁保证**：BOM 接货 `PullBOMResultFromODSAsync`（`BOMResultPullService.cs:56`）**仅夜间批跑**（`NightlyBatchOrchestrator.cs:121`）调用，白天候选没有 BOM 展开时机——新插订单的 BOM 如果白天不同步，排程直接无 Routing 可用。谁负责、何时保证？
- **Q2 插单的语义**：插单试排是「**加进来看冲突**（新单排进剩余产能，基线单不动）」还是「**允许挤掉基线单**（新单抢占，基线单被推后）」？两种语义对 1号位 的约束/排序完全不同，且影响「不可采用」红线的判定。
