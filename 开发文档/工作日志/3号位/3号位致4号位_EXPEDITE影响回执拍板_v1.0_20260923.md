## 一、拍板逐项

### P0-1【拍板 (a)】Candidate 页新增「EXPEDITE 影响范围」展示

**依据（冻结裁决原文含答案，非新开业务）**：
- 0号位 Q4-B §六：「V1 不建设自动损失优化模型。白天重排需要输出变化与影响范围，由业务人员判断是否接受」，并给出输出示例：
  ```
  EXPEDITE订单：SO10001
  影响订单：SO10002 / SO10003
  变化：原计划日期 → 新计划日期
  影响原因：EXPEDITE资源竞争
  ```
- v1.4 §十A 触发后由业务人员比对确认——「输出影响范围供业务确认」是**已冻结要求**，前端必须有承接位。

**给 4号位**：
- 新增 UI 模块 + 后端 `GET /api/candidate/{id}/expedite-impact`（路径见 P1-2 契约草案）。
- 展示形态参考 0号位 输出示例：EXPEDITE 单、受影响单清单、原→新计划日期、影响原因。
- 工作量 1~2 人天（前端 + 后端端点）确认可行，属 3号位/4号位 侧实现，不涉 2号位 DDL。

### P0-2【拍板 (a)】§10A.1 EXISTING_ORDER_ADVANCE 是 EXPEDITE 唯一入口

**依据**：
- v1.4 §十A 五入口契约：仅 10A.1 以 `orderTargets`（Demand）为对象、可挂 `PriorityMode: EXPEDITE`；其余四入口（GANTT_ADJUSTMENT / EQUIPMENT_FAILURE / RESOURCE_CALENDAR / DOMAIN_MANUAL_RESCHEDULE）为 Task 级 / 中断级 / 单 Domain 重排，恒 NORMAL 或禁 EXPEDITE。
- Q4-B §一 的 4 种适用场景（新增插单 / 已有提前 / 业务优先级提升 / 其他优先需求）是**Demand 语义说明**——说明 EXPEDITE 不限定「白天新增订单」，**不是新增 4 个 UI 入口**。

**给 4号位**：维持现状，不新增入口；`runScope.ts` 八码↔PriorityMode 矩阵不变。

### P1-1【非 V1 范围】CTP 入口不落地

**依据**：
- Q4-B §三 区分 CTP 与 EXPEDITE：CTP=承诺评估（按当前逻辑评估最早可承诺、不大调既有计划）；EXPEDITE=可重排可调整计划寻新方案。
- V1 范围=白天 Candidate 重排 + 影响确认，不含销售报价承诺评估 → **CTP 不在 V1**，§三 区分目前**纯为语义对照**，避免把 CTP 误当 EXPEDITE UI。

**归属预告**：若未来 V2 落地 CTP，按职责裁决查询类归 **5号位**（业务查询端点），非 4号位 新建页面。当前 4号位 无需建 CTP 页。

### P1-2【契约 3号位 起草 + 2号位 协助项】影响范围端点

- **契约**：由 3号位（Candidate / RunLifecycle 查询 Owner）起草端点契约，随 P0-1(a) 实施同步交付 4号位。端点草案：
  - `GET /api/candidate/{id}/expedite-impact`
  - DTO：`{ expeditedOrder: OrderImpactDto, affectedOrders: OrderImpactDto[], protectedOrders: OrderImpactDto[], changes: ChangeEntry[] }`
    - `OrderImpactDto`: `{ orderId, orderCanonicalId, originalDate, newDate }`
    - `ChangeEntry`: `{ orderId, before, after, reason: 'EXPEDITE_RESOURCE_CONTENTION' }`
  - 返回时机：实时计算（Candidate 已产排程结果，派生影响范围，非选购决策点，无需预计算缓存）
- **数据可给性**（「受影响单」是否可从排程结果派生）是 **2号位 能力**，非裁决项——随本函作为**协助项**备查 2号位，确认可派生即落地，无可派生字段则 3号位 另补投影契约。不需要 2号位 确认函，仅一条随回执带去的协助项。

### P1-3【4号位 直通 5号位】OrderCanonicalId 与 Demand 实体关系

- 按「涉及 5号位 由 4号位 直通」，3号位 不判断不协调。
