## 一、审计目的与结论

### 1.1 目的

v1.1 发布后（2026-08-29），lps 后端已按 G1/G2/G3/G5/G6/G7/G8/G9/G10 全部回写实现（v1.1 文末注），3↔4 联调可以启动。但 **v1.1 在覆盖前端 U04/U05/U06/U09/U14/U16-U18/U20 验收点时存在具体字段缺口**，必须先识别清楚、约定补齐口径再开始联调，否则前端 mock 切真实后会出现"调通但数据不够"的尴尬局面。

### 1.2 结论

| 维度 | 状态 |
|---|---|
| v1.1 接口总表（一/§二 A1-A13、B、C1、D、E、F、G1-G8）| ✅ 完备 |
| lps 后端落地 | ✅ 完备（详见 [lps/LPS.APS.Web/Controllers/GovernanceController.cs](../../lps/LPS.APS.Web/Controllers/GovernanceController.cs) + [ScheduleController.cs](../../lps/LPS.APS.Web/Controllers/ScheduleController.cs)）|
| 前端类型与路径对齐 | 🔴 需改造（详见 §六）|
| **3 号位 v1.2 增补** | 🟠 **本审计提出的 6 项缺口**（详见 §三、§五）|

**核心建议**：v1.1 基础上**补一份 v1.2 增量规格**（或 v1.1 附录 G2-b / H1），覆盖本审计的缺口 A、B、C、D，缺口 E/F 可在 v1.2 一并处理或后置。

## 二、6 个具体缺口（按重要度排序）

### 🔴 缺口 A：G2 GanttDataDto 字段严重不足

**影响验收点**：U04 / U05 / U06 / U14 / U16-U18 / U20 + 4号位主文档第 6、11 节

**v1.1 §二 G2 现行规格**（最小集）：

| 资源 Resource | 任务 Task |
|---|---|
| `ResourceId, ResourceCode, ResourceName, FactoryId, ProductionDepartmentId` | `TaskId, TaskNo, OrderId, OrderNo, MaterialId/Code/Name, ResourceId, OperationCode, OperationSeq, Quantity, UOM, PlannedStartTime, PlannedEndTime, Status, IsDelayed` |

**lps 后端 [GanttDataDto.cs](../../lps/LPS.APS.Application/Services/Query/Dto/GanttDataDto.cs) 当前实现**：与 v1.1 最小集一致。

**4号位前端需要但未在 G2 中定义**（按 4号位验收场景）：

| 字段 | 4号位页面 | 验收场景 |
|---|---|---|
| `Resource.domainKey` | Overview / Gantt | U01 多 Domain 染色分组 |
| `Resource.factoryName` / `productionDepartmentName` / `stage` | Gantt Drawer | 资源上下文展示 |
| `Resource.unavailableWindows[]`（from/to/reason/impactedTaskIds[]）| Run / Gantt | U20 设备故障不自动 Pause，仅展示 |
| `Task.domainKey` | Gantt / Run | U01 |
| `Task.netQty` + `Task.plannedProcessQty` | Gantt Drawer / Order Pegging | U05 净需求 vs 含良率补偿 |
| `Task.lockMarker` | Gantt 任务条 | U08 Demand Protection 锁标记 |
| `Task.taskShare[]`（orderId/orderNo/shareQty/shareRatio）| Gantt Drawer / Order | U04 多 Order 共担一个 Task |
| `Task.taskSegments[]`（segmentSeq/startTime/endTime/qty/qtyRatio/reason）| Gantt 任务条多段 | U06 数量-时间分段（40+60 不压成 100）|
| `Task.crossDomainBlocked` + `Task.crossDomainBlockReason` | Gantt / Candidate | U14 跨 Domain 阻挡 |
| `Task.factType`（FACT/RESULT/ESTIMATED/RECOMMENDATION）| Gantt / Order | 4号位主文档 §二.2 四类信息标签 |
| `Task.mesEligible` + `Task.mesIneligibleReasons[]` | Run / Gantt | U16-U18 MES 下发资格 |

| `Task.upstreamStageBlocked` + `Task.upstreamStageCode` | Gantt Drawer / Explanation | 第 11 节上游 Stage 阻挡 |

**建议**：v1.1 增加 **§二 G2-b** 子节，明确以上 16 个字段的来源、是否 nullable、性能取舍（建议 List 可空、避免一次拉所有 Reason 全量）。其中 Task.delayReasons 的 issueCategory 枚举在 v1.1 §三 ② 已隐含（DATA_ISSUE / SCHEDULING_ISSUE）。

- ✅ 最小人工确认：F2 `/api/Governance/plan-version/{id}/confirm-candidate`
- ✅ 激活：F3 `/api/Governance/plan-version/{id}/activate-candidate`

**4号位前端 [Candidate.vue](../../frontNew/src/views/Aps/Candidate.vue) 需要的复合 DTO**（当前 mock 在 [candidate.ts](../../frontNew/src/api/aps-v1/candidate.ts) 自行组装）：

| 字段 | 来源归属 | 建议 |
|---|---|---|
| `taskChangeSummary.{added, removed, timeShifted, resourceChanged, crossDomainBlocked}` | **3号位**（PlanVersionRepository 可算）| **新增 H1 端点** |
| `impactSummary.{impactedOrderCount, newDelayCount}` | **3号位** | H1 同上 |
| `impactSummary.{estimatedOnlyCount}` | 2号位（订单级估算）| 4号位文档 §7 |

| `reasons[]`（reasonCode/description/factType）| **3号位 / 2号位边界灰区** | **需 2号位文档确认** |

**建议 v1.2 新增端点 H1**：

| 项 | 规格 |
|---|---|
| 方法+URL | `GET /api/Governance/plan-version/{candidatePlanVersionId}/compare-with/{basePlanVersionId}` |
| 用途 | Candidate 对比页核心数据：候选 vs 基础的 Task/Order 影响 |
| 入参-Path | `candidatePlanVersionId` (int, 必填>0)、`basePlanVersionId` (int, 必填>0) |

| 校验规则 | 两版本存在；候选 `Status=CANDIDATE`；基础可任意状态 |
| 详细需求 | 复用 PlanVersionRepository 双版本 JOIN；TaskChangeSummary 基于 FinalTask 主键差集；CrossDomainBlocked 复用 G7 域依赖 |

> `reasons[]` 与 `estimatedOnlyCount` 不在本端点范围内，需 2号位文档对齐后单独约定。

### 🟠 缺口 C：MES 资格判定数据源缺失

**影响验收点**：U16（资格 ELIGIBLE）、U17（不可下发原因 INELIGIBLE）、U18（UNKNOWN 后端未判定）

**问题**：4号位 [Run.vue](../../frontNew/src/views/Aps/Run.vue) 顶部展示 MES 资格样本（7 类原因）+ 统计；v1.1 **既无独立 MES 资格端点，G2 GanttDataDto 也未含 `mesEligible` 字段**。

**建议**：

| 项 | 规格 |
|---|---|
| 归属 | 3号位（MES 资格在求解器收口时已计算，存 FinalTaskDraft）|
| 落地方式 | **G2-b 增量**（合并入缺口 A）：`GanttTaskDto.mesEligible` + `mesIneligibleReasons[]`（取值域：`CANDIDATE`/`UNLOCATED`/`NO_PI`/`PLANNING_PLACEHOLDER_DEPENDENCY`/`OUT_OF_DISPATCH_WINDOW`/`CANCELLED`/`OUT_OF_FROZEN_WINDOW` 等，4号位主文档第 16 节硬枚举）|
| 4号位消费 | Run.vue 客户端聚合 mesEligible 分布；Gantt Drawer 展示每个 Task 的资格与原因 |
| 与 v1.1 边界 | 3号位写"是否可下发"事实；4号位只展示 + 聚合；**不下发动作本身由 MES 域负责（4号位主文档 §16）**|
