下面把几个关键修改解释清楚。

### C2-1：不要在“读取Snapshot”时重新判断一遍谁是当前默认版本

3号位实施包已经明确：一次Run冻结`StrategyProfileVersionId`及对应RuleSet/ParameterSet，一旦Run开始，即使之后发布新规则，本Run也不能变化。

所以准确过程应是：

```text
创建ScheduleRun
→ 选择/校验当时有效的PUBLISHED StrategyProfileVersion
→ ScheduleRun.StrategyProfileVersionId冻结
→ 2号位按这个VersionId获取Snapshot一次
→ 整个Run使用同一Snapshot
```

不是：

```text
每个Domain开始
→ 再去找“现在最新的PUBLISHED”
```

否则理论上又可能漂移。

---

### C2-3：不要冻结SQL代码本身

这里3号位写得稍微过头了：

> “2号位现有SQL保持不变。”

跨号位契约不应该规定SQL必须一字不改。

当前冻结接口本来定义的是：创建ScheduleRun时如果未指定`StrategyProfileVersionId`，按RunType选择默认PUBLISHED版本；如果明确指定，就使用指定版本。

DDL同时保证**同一个StrategyProfile内部**只有一个`IsDefault=1 AND PUBLISHED`版本。

因此v0.2写成：

> **未显式指定StrategyProfileVersionId时，按RunType获取当前有效且无歧义的默认PUBLISHED版本；3号位负责发布/默认版本治理。具体查询SQL属于2号位实现，不作为本契约冻结内容。**

这样就够了。

这**不是要求2号位现在新增一个整改项**。2号位回来后只检查现有SQL是否满足这个语义即可。

---

### C2-4：Cache Key内容冻结，字符串不冻结

3号位实施包真正的要求只是：

> Snapshot可缓存；Cache Key必须包含VersionId；一次Run不逐笔查数据库。

所以：

```text
frozen-strategy-snapshot:123
```

当然可以。

但没有必要成为跨团队协议。

以后2号位写成：

```text
APS:StrategySnapshot:123
```

业务一样正确。

因此只冻结：

> **Cache Key必须含StrategyProfileVersionId，并保证不同版本绝不互相污染。**

### C2-5：六块结构基本正确，但漏了一个重要内容——Planning Yield

3号位实施包给出的Snapshot示例确实是六块：


所以这个大结构不用重新设计。

但是同一份3号位实施包明确要求3号位维护**计划良率（Planning Yield）**，由2号位读取后计算`NetOutputQty → PlannedProcessQty`。

而确认单只列六块名称，看不出PlanningYield到底放在哪里，因此我不能替你确认“无遗漏”。

v0.2只需要明确：

> `PlanningYield`必须进入FrozenStrategySnapshot。

不需要因此增加新表、新版本体系。可以作为`Supply`中的独立子配置，或者契约中明确其它合理归属，**重点是不能漏掉**。

同时建议Snapshot头部明确：

```text
StrategyProfileVersionId
RuleSetVersionId
ParameterSetVersionId
```

便于2、1、5号位联调和问题追溯。

## C2-6：我直接替2号位裁决为“2号位抽”

这里不要再等2号位拍板。

正式链：

```text
3号位
FrozenStrategySnapshot
        ↓
2号位一次装载
        ↓
2号位抽取FrozenFactParameters
        ↓
5号位复杂事实接口
```

5号位实施包本来也写的是“一次Run参数由3号位冻结，2号位装载后传给5号位”。

我**不建议**让：

```csharp
Snapshot.ToFrozenFactParameters()
```

直接成为3号位DTO的方法。

因为那样3号位的数据结构就开始认识2↔5的接口DTO，反而形成隐形：

```text
3号位 → 5号位
```

依赖。

更干净的是2号位集成层有一个很小的Mapping：

```text
FrozenStrategySnapshot
→ FrozenFactParameters
```

这正是2号位“主流程编排”的正常职责，不是给2号位增加业务判断。

# 5号位这三项里，C5-1需要明显收缩

当前确认单给`FrozenFactParameters`放了：

```text
DefaultPurchaseLt
OverdueMargin
ArrivalToUsableOffsets
ProtectionTrigger
InventoryAvailability
ProcurementSort
```



后面三个不应该给5号位。

因为：

```text
ProtectionTrigger
InventoryAvailability
ProcurementSort
```

都是：

> **3号位治理 → 2号位执行。**

5号位不做Demand Protection最终执行、不做Supply选择、不做Allocation。关键接口冻结已经明确这一职责。

5号位采购事实真正需要的是：

```text
DefaultPurchaseLt
OverdueMargin
ArrivalToUsableOffsets
```

因为5号位要用这些参数标准化Effective ETA和AvailableTime。它的实施包明确：

* Manual ETA > ERP ETA > Default LT；
* Default LT由3号位治理参数；
* 逾期时使用Margin；
* Arrival-to-usable使用Warehouse Offset；
* 5号位形成标准Timed Supply。

### 因此FrozenFactParameters当前建议最小化为

```text
StrategyProfileVersionId   // 追溯父Snapshot

DefaultPurchaseLt
OverdueMargin
ArrivalToUsableOffsets
```

如果实现中按Material/Warehouse存在多条，就是对应集合即可。

**目前不要增加：**

```text
UNLOCATED容忍比例
Position允许不闭合阈值
ProtectionTrigger
InventoryAvailability
ProcurementSort
DemandPriority
SolverStrategy
CandidateGuardrail
```

特别是PI Position不能靠“容忍比例”允许数量不闭合。冻结规则始终是：

> `Σ PositionQty = ERP RemainingQty`

无法定位就进入UNLOCATED；无法闭合且无法保守定位才是严重Issue。

如果代码计算decimal时未来需要`0.000001`这种纯数值精度epsilon，那是算法技术细节，不建设成业务参数。
