# 二、需 0号位 裁决的核心问题

## 问题 1：交接边界——"增量实现"还是"接管现有登录链路"？

- **现状**：现有登录链路全部代码（AuthService/AuthController/Auth 仓储/AuthDbContext）归属 **2号位**。
- **方案 A（增量实现，3号位 建议）**：3号位 仅在现有登录基础之上**新增** RBAC 能力——权限码定义、权限判定过滤器、角色/权限管理接口。不修改任何 2号位 现有 Auth 文件。
- **方案 B（接管现有登录链路）**：3号位 接手 AuthService/AuthController/仓储，可修改现有登录/刷新/登出逻辑。**需 0号位 书面交接裁决**，否则 3号位 一动这些文件即违反"不越位"红线。

## 问题 2：访问控制接入范围——"从宽"还是"严格"？

- **现状**：现有接口仅治理/排程控制器（除 me/logout 外）**无任何授权校验**。
- **方案 X（从宽接入，3号位 建议）**：RBAC 落地第一阶段**只保证登录校验**，治理/排程接口默认不强制权限码；权限码细粒度控制后置到第二阶段。避免阻塞 3↔4 联调与现有集成测试。
- **方案 Y（严格接入）**：按功能域给现有接口配置权限码。**影响面**：4号位 前端所有请求需携带 token+权限码，现有集成测试未授权场景需同步改造，联调返工风险高。

## 问题 3：现有 2号位 Auth 代码的最终处置

- **选项 1（保留 2号位 Owner）**：现有 Auth 文件维持 2号位 归属，3号位 只读消费其登录结果，RBAC 新代码全部放 3号位 新文件（建议）。
- **选项 2（交接给 3号位）**：0号位 书面裁决将现有 Auth 文件收编为 3号位，工作树提交时由 3号位 一并接管（需明确与 2号位 未提交改动的区分）。

## 问题 4：APS_Auth 库 DB 变更归属（红线 #6）

- RBAC 若需新增表/字段（如权限码种子表、用户-角色-权限关联扩展、数据权限范围配置），属 **APS_Auth 库结构变更**。
- **3号位 建议**：确认维持红线 #6——DB 结构变更由 **2号位 专属执行**，3号位 提交 DDL 变更申请、提供实体/仓储/DbSet 交付，不直接 ALTER。

# 三、影响面分析（对现有项目）

1. **职责归属冲突（最关键）**：RBAC 归 3号位 与现有 Auth 代码归 2号位 直接重叠。未经边界裁决，3号位 无法动工或一开工即越位。
2. **现有登录链路不受影响**：只要采用增量方案，login/refresh/logout/me 行为不变，现有客户端与 4号位 联调零影响。
3. **访问控制行为变化（仅严格方案）**：接口加权限码会改变现有接口的访问控制行为，波及 4号位 联调与集成测试。从宽方案无此影响。
4. **契约（红线 #5）**：新增 RBAC 管理端点属"新增接口"，不改既有签名、不违反 #5；需在契约文档登记。若改既有 Auth 接口签名（LoginRequestDto 等）必须先更新契约。
5. **任务清单 v2.0**：RBAC 成为新的 3号位 任务域（自主侧 + 协调侧各增条目），待本裁决后纳入。
6. **工作树提交**：现有 Auth 文件归 2号位，3号位 提交 RBAC 新增文件时须与 2号位 的 Auth 改动区分，避免一并入库。

# 四、3号位 建议方案（待 0号位 确认）

1. **交接边界**：采用**方案 A 增量实现**——RBAC 新代码（权限码目录 + 权限判定过滤器 + 角色权限管理接口 + 种子数据）全部为 3号位 新增文件，不修改 2号位 现有 Auth 文件。
2. **接入范围**：采用**方案 X 从宽接入**——第一阶段仅登录校验，权限码细粒度控制后置第二阶段。
3. **DB 变更**：维持红线 #6，2号位 专属执行，3号位 提交变更申请。
4. **契约**：RBAC 管理接口作为新增契约章节登记；既有 Auth 契约不动。
