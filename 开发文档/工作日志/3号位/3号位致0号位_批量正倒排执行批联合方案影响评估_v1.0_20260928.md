## 〇、一句话

Batch Policy 的硬 Min/Max/Preferred 是**键控（Material + ProductionDepartment）**需求，现有治理容器是**单值全局块**，两者天然不匹配；最小承接点**不是新建表，而是 `ParameterSetVersion.ContentSnapshotJson` 新增「BatchPolicy 键控列表子块」**（复用既有冻结/版本/追溯主链），方向（正倒排）则从 `SolverStrategyBlock.Mode` 三值扩展为 AUTO/首选软语义 + 键控。当前 `Operation` 级 Min/Max 是**死列（无消费）**，退出主链零破坏；`TaskSplitRuleConfig` 仅 DDL 存在、代码无实体，是否启用需 0号位 定。

## 二、逐项影响判断与建议（§5.2–§5.7）

### 2.1（§5.2）Batch Policy 载体选择 —— **推荐：新增快照子块（键控列表），不建表**

四个候选逐一判定：

| 候选 | 键/形态 | 判定 |
|---|---|---|
| `TaskSplitRuleConfig` | Material + ResourceGroup | 粒度最接近，但**不在治理引擎内**（无版本/冻结/追溯），且是 DDL 时代产物、代码未接线 |
| `RoutingPlanningParam` | Material + Route + Path + **Operation** | **太细**；§2.3 明令 Batch 按 Material+Department 而非 Operation |
| `ParameterSet` / `ParameterSetVersion` | 块 JSON（全局单值） | 版本/冻结/追溯完备，但**无键控** |
| `StrategyProfile` | 仅 RunType | 无键控、无块 |

**B 判断**：新粒度"Material + ProductionDepartment → 硬 Min/Max/Preferred"是**键控查找表**语义，而治理容器是**版本化块快照**语义，二者正交。

**C 建议**：**复用 `ParameterSetVersion.ContentSnapshotJson` 新增第 ⑧ 子块 `BatchPolicy`，内容为键控项列表**：

```
BatchPolicy = [ { MaterialId, ProductionDepartmentId, MinExecutionBatchQty, MaxExecutionBatchQty,
                   PreferredBatchQty, AllowSplit, AllowMerge } , ... ]
```

- 随 FrozenStrategySnapshot 一并冻结/版本化/追溯（复用 `FrozenStrategySnapshotProvider` 装载链，仅加一 `DeserializeParameterSetBlock<List<BatchPolicyEntry>>`）。
- 2号位 装载后构建 `Dictionary<(Material, Dept), BatchPolicyEntry>` 供 1号位 查找。
- **不新建表、不新建治理引擎**（遵 §5.2「不要直接假设必须新建表」+ §三「优先保护 2号位主链」）。
- 代价：键控列表在 JSON 内不可 SQL 查询——但 Batch Policy 本就是**整包加载**语义（与其余 6 块一致），无按键单查需求。

> 备选（仅当 0号位 坚持"主题规则表"路径）：`TaskSplitRuleConfig` 迁移到 Material+ProductionDepartment 并接线规则参数引擎。**工作量大、破坏 §三主链优先原则，3号位 不建议。**

### 2.2（§5.3）Operation 级 Min/Max 处置

1. **哪些代码消费**：`MinBatchSize/MaxBatchSize` **无消费者**（死列）；`TransferBatchSize` 2 处（§1.3）。
2. **是否仍有真实工艺含义**：`TransferBatchSize` **有**（工序间流转单位，驱动 StageOverlap 阈值启动）→ **保留**；`Min/Max` 是"加工批量"规划语义（无 ODS 来源），新方案下该语义上收到 Batch Policy。
3. **TransferBatchSize 是否继续保留**：**是**，它与 Execution Batch 正交，是重叠/流转机制的一部分。
4. **Min/Max 如何退出主链**：因其**本就消费=0**，直接"停读 + 文档退役标注"即可，无需迁移。
5. **是否兼容保留字段**：物理列保留（红线 #6 DDL 归 2号位，不主动 DROP），代码侧标 `[Obsolete]`/注释退役，不再进任何主链。
6. **如何避免一次性破坏**：不 DROP、不删实体属性、不改任何既有消费（本就无消费），仅文档契约登记"退役 + 语义移交 Batch Policy"。

### 2.3（§5.4）TaskSplitRuleConfig 处置

- **能否最小迁移到 ProductionDepartment**：能（`ResourceGroupId` → `ProductionDepartmentId`，替换已废弃的兼容维度）。
- **是否新增 `ProductionDepartmentId`**：若启用该表则**是**。
- **`ResourceGroupId` 是否兼容保留**：是（保持既有"废弃保留"口径）。
- **`MinimumOrderQuantity`/`EconomicOrderQuantity` 字段名是否重新解释**：建议**物理列名沿用、契约/接口层用新语义名**（MOQ→最小执行批、EOQ→最大执行批），避免 DDL 漂移（冻结顺序=业务→数据→接口→代码；命名由 0号位 定）。
- **`BottleneckSplitStrategy` 是否退出硬批量规则**：**是**。§2.3 已明令 Batch 规则**不按动态瓶颈设备**；`PREFER_SPLIT/PREFER_MERGE` 本就是软偏好，应降级为 Solver 软偏好（并入 Scheduling Policy），不进硬 Min/Max 真相。
- **是否保留为 Solver 软偏好**：是（`PREFER_SPLIT/PREFER_MERGE` → 方向/批偏好；`NonBottleneckStrategy` 同理）。
- **总判断**：此表可作为"键控 Batch Policy 持久化"的候选落点，但**当前无代码接线**，启用成本≈新接一条治理链；故 3号位 倾向"短中期冷藏、由快照子块承接"（见 §2.1），是否正式废弃/迁移交 0号位。

### 2.4（§5.5）Batch Policy 字段与现有承载映射

| 新字段 | 现有承载 | 判断 |
|---|---|---|
| `MinExecutionBatchQty`（硬） | 无（`RoutingPlanningParam.MinBatchSize` 死列；`Split.MinBatchQty=0.1` 是全局软值） | **新增，键控** |
| `MaxExecutionBatchQty`（硬） | 无 | **新增，键控** |
| `PreferredBatchQty`（软） | 无 | **新增，键控** |
| `AllowSplit` | `Split.LimitMandatorySplit`（近似，全局） | 硬开关进 Batch Policy；搜索预算留 `Split` |
| `AllowMerge` | `SolverStrategyBlock.AllowMerge`（全局=false） | 键控化（Batch Policy 承载），全局默认回落 |
| `MaxOptimizationSplitCount` | `Split.MaxOptimizationSplitCount`（=3，全局） | **保留在全局 `Split`**（V1 搜索预算，非键控） |

**B 判断**：`Min/Max/Preferred` 必须键控；`AllowSplit/AllowMerge/MaxOptimizationSplitCount` 已存在但为全局值。分层原则——**键控硬约束进 Batch Policy，全局搜索预算/软偏好留在 SolverStrategyBlock**，二者并存。

### 2.5（§5.6）Policy 命中优先级（最小可解释）

```
① 精确命中：MaterialId + ProductionDepartmentId 有 Entry        → 采用该 Entry
② 部门默认：ProductionDepartmentId = 0/NULL（"该物料任意部门"）→ 采用该默认
③ 全局默认：无任何 Entry                                       → 回落 SolverStrategyBlock.Split
                                                        + AllowSplit/AllowMerge 全局默认
④ 缺失策略：不 FAIL，回落 ③（V1 语义：Batch Policy 是"可选精细约束"，
            非"无即无法运行"的必备项；FAIL-closed 只保留给快照块缺失）
```

- 不建设万能 `RuleCondition`/`RuleExpression`（遵 §5.6）。
- 命中链确定、可解释、可测试。

### 2.6（§5.7）Scheduling Policy（正倒排）

**B 判断**：
- 当前 `SolverStrategyBlock.Mode` = 三值硬排向（`Forward/Backward/Mixed`），**无 AUTO、无 PREFERRED 软语义、无键控**。
- 新要求 = 四值（`AUTO / FORWARD_PREFERRED / BACKWARD_PREFERRED / MIXED`）+ 键控（ProductFamily+Factory+Stage+OrderType + Material 例外）+ 阈值（Slack/Coverage/Solver 预算/Batch 候选上限）。

**C 建议（最小表达）**：
- **方向值域扩展**：`SolverStrategyBlock.Mode` 语义从"硬排向"扩展为"首选排向+AUTO"（或新增 `Direction` 字段并行、保留旧 `Mode` —— **交 0号位 定名/定去留**，见 §四）。
- **阈值字段**：`SlackThreshold`、`CoverageThreshold`、`SolverSearchBudget`（`MaxIterations`）、`BatchCandidateCap` —— 均为静态参数。
- **Scope 键控**：复用 Business Scope 载体（ProductFamily+Factory+Stage+OrderType + Material 例外），**不往 `StrategyProfile` 表加列**（当前实体本无 scope 列，加列属 DDL 变更且需 2号位，还应与 Business Scope 投影统一）。
- **红线遵守**（§5.7 + §7.2）：3号位 只配**静态阈值/枚举/预算**，**不配** `如果Risk=X就拆300`、`如果Operation=NC就Backward` 类动态 IF-THEN（归 1号位）；AUTO 的选向算法由 1号位 按 Slack/Coverage/库存上下文动态决定，3号位 只给阈值。

## 四、仍需 0号位 裁决的问题（仅业务事实分歧，非技术设计）

1. **Batch Policy 载体取向**：块内键控列表（3号位首推，不建表） vs `TaskSplitRuleConfig` 主题规则表迁移（需接治理引擎、成本高）。
2. **`SolverStrategyBlock.Mode` 去留**：值域原位扩展（`Mode` 变 AUTO/PREFERRED/MIXED） vs 新增独立 `Direction` 字段、保留旧三值 `Mode`。
3. **Scheduling Policy 的 Scope 载体**：是否复用 Business Scope（`IDataScopeService`/ScopeJson），而非 `StrategyProfile` 加 scope 列——当前代码 `StrategyProfile` 无 scope 列，与 §5.7 表述存在落差，需 0号位 确认口径。
4. **`TaskSplitRuleConfig` 正式命运**：启用迁移 / 正式废弃 / 短中期冷藏（字段并入新 Batch Policy）。
5. **缺失 Policy 兜底**：回落全局默认（3号位建议） vs FAIL-closed（若要求硬约束显式配置）。
6. **字段命名**：`MinExecutionBatchQty/MaxExecutionBatchQty` 新语义名 vs 沿用 MOQ/EOQ 物理列名（影响 DDL 是否漂移）。

> 其余（DTO 命名、Service 位置、类拆分、最小改法）按 §十属各号位技术方案，不上交。
