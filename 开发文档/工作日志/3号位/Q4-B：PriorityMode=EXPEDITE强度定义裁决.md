
下面是建议给3号位的正式裁决。

---

# Q4-B：PriorityMode=EXPEDITE强度定义裁决

## 0号位裁决结论

**EXPEDITE不是简单的订单排序标签，也不是仅用于新增订单之间的优先级比较。**

EXPEDITE表示：

> 用户指定某需求订单需要优先满足，系统在白天Candidate重排中调整需求优先级，并允许该需求与当前计划中的可调整需求重新竞争有限资源，以寻找满足加急目标的可行计划。

---

# 一、EXPEDITE适用范围

EXPEDITE不限定为“白天新增订单”。

适用场景包括：

1. 新增客户订单，需要快速插入；
2. 已有订单客户要求提前；
3. 已存在需求但业务优先级提升；
4. 其他业务明确要求优先保障的需求。

因此：

```text
PriorityMode=EXPEDITE
```

表示：

> 本次Candidate计算中，该需求订单进入加急优先模式。

不是：

> 新订单自动等于EXPEDITE。

---

# 二、EXPEDITE调整对象

## 不是Task。

调整对象：

> 需求订单（Demand）。

业务链路：

```
需求订单优先级调整
        ↓
重新进行Demand排序
        ↓
重新Pegging供需承接
        ↓
重新生成Task
        ↓
重新有限产能排程
```

不采用：

```
直接移动某几个Task
```

作为插单逻辑。

---

# 三、EXPEDITE与NORMAL CTP区别

## NORMAL CTP

业务含义：

> 按当前正常计划逻辑，评估该需求最早可承诺时间。

特点：

* 不要求大规模调整已有计划；
* 主要用于承诺评估。

---

## EXPEDITE

业务含义：

> 如果该需求必须提前，系统允许调整当前可调整计划，重新寻找满足方案。

因此：

EXPEDITE不是：

“排在CTP新增订单前面”。

而是：

> 允许进入当前计划重新优化范围。

---

# 四、不可插入订单如何处理

这里明确：

**不可插入 ≠ 不参与Candidate计算。**

正确理解：

某些订单具有保护约束：

* 已形成执行事实；
* 已锁定计划；
* 业务明确不可调整。

这些订单：

仍然作为本次排程输入存在。

但是：

> EXPEDITE不能强行改变其保护优先级或执行约束。

例如：

当前：

```
1. 订单A（已开工）
2. 订单B（正常）
3. 订单C（正常）
```

新增：

```
订单D（EXPEDITE）
```

结果允许：

```
1. 订单A
2. 订单D
3. 订单B
4. 订单C
```

不允许：

```
1. 订单D
2. 订单A
```

---

# 五、EXPEDITE不能突破的约束

分为三类。

---

## 1. 执行事实约束

属于已经发生的生产事实。

例如：

* 已完工；
* 已开工；
* 已发生领料等执行证据。

这些形成保护边界。

实现：

排程时不可被EXPEDITE重新安排。

---

## 2. 业务保护约束

例如：

* Firm/Frozen计划；
* 已确认不可调整的需求。

含义：

EXPEDITE不能强行抢占其保护位置。

注意：

不是“不允许其他订单延期”。

而是：

不能无视已有业务承诺。

---

## 3. 技术硬约束

必须满足：

* 物料AvailableTime；
* Resource Calendar资源可用时间；
* Routing工艺约束；
* 有限产能约束。

---

# 六、V1是否做损失控制？

## 裁决：

V1不建设自动损失优化模型。

不增加：

* 延期成本；
* 订单保护权重；
* 损失评分。

原因：

V1已经确定：

> 白天重排需要输出变化与影响范围，由业务人员判断是否接受。

因此：

系统输出：

例如：

```
EXPEDITE订单：
SO10001

影响订单：
SO10002
SO10003

变化：
原计划日期 → 新计划日期
影响原因：
EXPEDITE资源竞争
```

由人工确认。

---

# 七、3号位实现要求

3号位无需新增：

* EXPEDITE_WEIGHT；
* EXPEDITE_SCORE；
* PriorityFactor。

只需明确：

## PriorityMode：

```
NORMAL
EXPEDITE
```

并定义：

* EXPEDITE作用范围；
* 与Demand排序关系；
* 不突破的保护边界。

---

# 八、最终一句话冻结

> EXPEDITE表示用户指定需求订单进入加急优先模式。在白天Candidate重排中，系统调整需求订单优先级，允许EXPEDITE需求与当前计划中的可调整需求重新竞争资源，并在新的需求排序基础上重新执行Pegging和排程。EXPEDITE不能突破已形成执行事实、业务保护约束以及物料、资源、工艺等硬约束。V1不自动计算牺牲成本，仅输出影响范围供业务确认。
