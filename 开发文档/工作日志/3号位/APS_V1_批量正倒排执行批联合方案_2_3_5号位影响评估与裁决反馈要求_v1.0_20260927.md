# APS V1 批量、正倒排与执行批联合方案——2号位、3号位、5号位影响评估与裁决反馈要求

**版本**：v1.0  
**日期**：2026-09-27（北京时间）  
**性质**：影响评估任务书；本轮只要求各号位AI结合现有代码做评估和反馈，**不要求立即修改正式代码**  
**适用对象**：2号位AI、3号位AI、5号位AI  
**中文口径要求**：中文业务解释为主；英文只用于代码字段、类名、接口名、状态名对照。

# 一、本轮工作方式

本轮不是“收到方案就改代码”。

本轮要求：

```text
先理解联合裁决
↓
对照自己现有代码
↓
判断哪些可以直接保留
↓
判断哪些必须修改
↓
判断会影响哪些接口/DTO/表/服务
↓
提出最小修改方案
↓
列出真实冲突和依赖
↓
提交给0号位统一裁决
```

在0号位完成统一裁决以前：

- 不允许自行改变冻结业务；
- 不允许各号位自己创造新的Batch定义；
- 不允许自行修改A/B/C定义；
- 不允许自行改变TaskNo/MES工单关系；
- 不允许先改正式DDL；
- 不允许因为实现困难把职责推给其它号位；
- 不允许另建第二套Demand/Supply/Pegging/Execution平台。

# 二、所有号位共同必须理解的业务母线

## 2.1 Task与MES

统一理解：

```text
Task.Id
= Operation级排程记录

TaskNo
= Execution Batch跨版本业务身份

一个TaskNo
↔ 一张MESWorkOrder

一个TaskNo
可包含多条Operation级Task.Id
```

## 2.2 Execution Batch

Execution Batch是：

> 同一大工艺/生产部门执行范围内，未来由一张MES工单承接的最终生产批。

## 2.3 Batch规则

硬Min/Max按：

```text
Material + ProductionDepartment
```

治理。

不按：

- Operation；
- Resource；
- 动态瓶颈设备。

## 2.4 A/B/C

A/B已有真实执行身份，不参加普通拆合批。  
C自由份额由1号位动态形成最终Execution Batch。

## 2.5 正倒排

不是：

```text
SO=倒排
MTS=正排
```

而是看：

- Demand Goal；
- NeedByTime；
- Slack；
- Inventory Coverage；
- Material；
- Execution；
- Firm/Frozen；
- Resource Reality。

## 2.6 责任链

```text
5号位
解释复杂事实
↓
2号位
形成业务数量真相、Pegging、A/B/C、运行输入
↓
1号位
Batch + Direction + 有限产能
↓
2号位
TaskNo和结果持久化
```

3号位负责规则/参数/策略治理，不参与当前运行计算。


在业务正确性相同前提下，优先方案B。

## 4.2 需要2号位重点评估的第一项：一个MES工单多Slice

当前需要支持：

```text
一个MESWorkOrder
→ RemainingNetQty
→ N个NextOperation Slice
```

例如：

```text
WO001 RemainingNetQty=700

200 → NC
300 → 挤丝
200 → 精修
```

请评估：

1. 当前ExistingExecutionContext是否默认“一WO一个StartOperation”；
2. 当前LogicalProductionDemand是否允许同一执行身份对应多Slice；
3. 最小DTO改法；
4. 如何保持同一ContinuationKey/执行身份；
5. 是否影响Q/E闭合；
6. 是否影响A/B分桶；
7. 是否影响DomainSolveRequest序列化；
8. 是否影响TaskNo继承。

2号位不得重新读取OperationProgress自己计算这些Slice。

## 4.3 第二项：Demand Goal如何从Pegging/Allocation整理给1号位

请评估如何最小增加以下运行语义：

```text
Qty

ProtectionLevel
NeedByTime
CustomerDueDate（可空）
InventoryTargetTime（可空）
BusinessPriority

```

要求：

- 不复制Pegging；
- 不改当前Q；
- 不把完整Pegging图推给1号位；
- 只整理1号位做Batch/Direction真正需要的目标信息。

请给出：

- 现有字段可复用项；
- 新DTO字段；
- 生成位置；
- 数据来源；
- 是否需要持久化，还是仅运行时对象。

## 4.4 第三项：Batch Policy怎么进入Solver

Batch Policy业务粒度：

```text
Material + ProductionDepartment
```

请评估：

1. 现有Frozen Parameter Snapshot怎么读取；
2. DomainSolveRequest是否已有通用参数块可复用；
3. 是否需要新增BatchPolicy DTO；
4. 一个Domain中不同Material/Department如何查找；
5. 缺失Policy如何处理；
6. 2号位只加载/冻结，不运行Batch算法。

## 4.5 第四项：ExecutionBatchKey返回后TaskNo如何归组

请重点检查当前代码是否存在：

```text
每个FinalTaskDraft
→ 生成一个TaskNo
```

这种假设。

新规则：

### A桶

```text
多个Operation FinalTask
→ 继承同一个OldTaskNo
```

### B桶

```text
同一个原MESWorkOrderNo
→ 本Run只生成一个新TaskNo
```

### C桶

```text
同一个ExecutionBatchKey
→ 一个新TaskNo
```

请列出：

- 当前TaskNo生成函数；
- 当前调用点；
- 修改点；
- 对事务持久化影响。

## 4.6 第五项：Task表同TaskNo多行

当前方案要求：

```text
TaskNo=T001

Task.Id=101 NC
Task.Id=102 挤丝
Task.Id=103 精修
```

请检查：

- 应用代码是否假设TaskNo唯一行；
- SQL是否存在唯一约束；
- 查询接口是否First/Single；
- MES下发是否按TaskId；
- Candidate Diff是否按TaskNo唯一；
- 版本追溯是否受影响；
- Task状态聚合是否受影响。

只反馈事实和最小修改方案，不要自行新建TaskHeader。

## 4.7 第六项：AllocationTaskShare

一个Execution Batch可以承接多个Demand，一个Demand也可以拆到多个Batch。

请评估：

- 现有AllocationTaskShare是否足够；
- Operation级Task都落Share，是否会重复计算业务归属；
- 是否需要“只在特定Operation记录业务份额”的规则；
- 或现有多Task份额链是否已能正确回溯。

这一项请特别谨慎，避免造成Demand数量重复统计。

## 4.8 第七项：MES下发

请确认当前MES下发到底按：

- Task.Id；
- TaskNo；
- 其它中间表键；

哪一个聚合。

目标规则：

```text
一个TaskNo
→ 一张MES工单
```

而不是：

```text
一个Task.Id
→ 一张MES工单
```

请给出当前代码事实和最小修改点。

## 4.9 第八项：库存覆盖上下文

本轮只要求评估，不要求立即实现完整Coverage算法。

请回答：

1. 当前InventoryBalance/Pegging/Allocation能否支持按仓库物料形成库存上下文；
2. “客户订单占用、顶层MTS占用、中间层MTS占用”当前能否区分；
3. 是否需要新的运行时InventoryCoverageContext；
4. 这个Context应在2号位哪里形成；
5. 应传给1号位什么最小字段；
6. 是否无需新增永久表。

## 4.10 2号位必须返回的评估格式

请输出：

- 可完全保留；
- 必须修改；
- 建议最小改动；
- 不建议修改；

# 十二、统一业务终态

所有号位最后必须共同理解：

```text
5号位给事实
↓
2号位给当前需求、Pegging、连续身份和业务目标
↓
3号位给冻结规则/参数/策略
↓
1号位决定C桶Execution Batch、正倒排和Operation有限产能
↓
1号位返回ExecutionBatchKey + Operation FinalTask
↓
2号位生成/继承TaskNo并持久化
↓
MES按TaskNo创建/继续一张工单
↓
MES执行事实下一FULL重新进入5号位
```

整个方案的技术优先级继续保持：

> **优先保护2号位现有代码和运行主链。**
