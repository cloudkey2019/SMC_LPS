## 二、6 项缺陷逐项整改计划

### N-01｜P0｜Setup 规则版本 Diff 存在 Department Scope 绕过

- **证据位置**：`SetupRuleService.cs:365-424`（GetDiffAsync 全量生成 Add/Mod/Remove）；`SetupRuleController.cs:263-279`（仅验 SetupView，未传操作者）；`ISetupRuleService.GetDiffAsync` 无 actor 参数。
- **整改方案**：`GetDiffAsync` 契约补受信 `actorUserId`（扩展接口，红线#5 契约先行）；服务内 `ResolveAllowedDeptCodesAsync` 过滤两版规则，**Added/Modified/Removed 数量与过滤后一致**；Controller 传入真实操作者。
- **测试**：A-only 变更 / B-only 变更 / Global / 无 Department 授权 / 「仅在一侧版本出现未授权规则」5 类判别用例。
- **协同**：`ISetupRuleService` 为 3号位 自有接口；落码前评估 4号位 前端对该端点调用并知会（契约同步）。

### N-02｜P0｜Setup 工序资源资格查询存在 Department Scope 绕过

- **证据位置**：`SetupRuleService.cs:283-332`（GetEligibilityAsync 回带资源/部门码，全程无 actor）；`SetupRuleController.cs:203-242`（SetupView 可查，不携带操作人）。
- **整改方案**：接口补 `actorUserId`；按 Department Scope 过滤资源及其展示属性（ResourceCode/ResourceName/DepartmentCode/StageCode）；**零授权空结果，Global 全量**。
- **测试**：A+B 资源仅授权 A ⇒ 仅回 A 且不泄露 B；无授权为空；Global 全量——与既有 Setup List 越 Scope 回归一致，**不依赖前端遮挡**。

### N-03｜P0｜Domain 定义用户态 GET 没有 Domain Scope 限制

- **证据位置**：`GovernanceController.cs:866-901`（列表/有效/详情三端点仅验 PlanView，直接调不带 actor 的 GetAllAsync/GetActiveAsync/GetByIdAsync）；`DomainDefinitionRepository.cs:25-60`（全量/按 Id 返回，无 Domain Scope 过滤）。
- **整改方案**：对面向登录用户的治理读端点施加有效 **Domain Scope** 过滤；**供内部运行使用的独立信任调用与用户查询过滤分离，不混用**。
- **测试**：A-only / Global / 无授权 / 按 Id 读取 B 域判别用例。

### N-04｜P1｜Domain 业务越权被错误返回 400 而非 403

- **证据位置**：`DomainDefinitionGovernanceService.cs:280-289`（EnsureDomainAllowsAsync 抛 InvalidOperationException）；`GovernanceController.cs:924-989`（Create/Update/Enable/Disable 捕获为 HTTP400）。
- **整改方案**：业务范围拒绝改抛 **`ScopeViolationException`** → 统一 403（与既有契约一致，见治理统一 ApiResponse 口径）；**参数格式非法仍 400**。
- **测试**：Controller/HTTP 层断言 403 与 400 分流（不只断言服务抛异常）。

### N-05｜P0｜Domain 活跃范围组合唯一性存在并发竞态

- **证据位置**：`DomainDefinitionGovernanceService.cs:70-176`（EnsureScopeComboUniqueAsync 与写分离）；`DomainDefinitionRepository.cs:76-129,137-159`（独立 SQL，SELECT COUNT 预检非事务锁定）；DDL 仅 `UQ_DomainDefinition_DomainKey`、`IX_DomainDefinition_Scope` 非唯一。
- **整改方案**：**检查 + 写置于同一事务**，业务键上复用 SQL Server 事务级应用锁 `sp_getapplock` 串行化（BatchPolicy 唯一有效期 P1-02 既有先例）。**不新增/修改冻结 DDL**（唯一约束变更须走既定流程，不私改）。
- **测试**：Create×Create / Enable×Enable / Update×Enable 交错 ⇒ 活跃范围组合唯一；不同 Scope 不串行化。
- **口径**：属并发条件下代码无法保证唯一性的静态证明；3号位 在治理写路径保证串行化，不宣称已出现实际重复数据。

### R-01｜P1（持续 OPEN）｜APS 业务写与 Auth 审计失败的最终一致性

- **证据位置**：`DomainDefinitionGovernanceService.cs:95-96,133-134,155-176`（先写 APS 业务、后 AuditAsync 独立写 Auth）；`:292-325`（开发注释承认「状态已落库、审计缺、需对账」）；`AuditLogRepository.cs:33-49` 真实写探针已修复并认可。
- **整改方案**：交付**可验证的审计失败对账/补偿办法** + **故障注入测试**（「APS 变更已提交、Auth 审计失败」⇒ 结果可识别、可对账、可补偿、恢复后可追溯）。属旧 P1 未闭环部分，方案需设计确认后落码，单独推进。
- **边界**：不以其他号位落库链路作为举证理由（0号位 已明确）。
