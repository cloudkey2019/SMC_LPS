## 一、背景与现状

P0-08「FAILED 恢复」当前只走了一半：`RecoverFailedRunAsync`（`LPS.APS.Application/Services/RunLifecycleService.cs:353-384`）为 FAILED 的 `ScheduleRun` 新建一条 RUNNING 重跑（`InsertForRecoveryAsync` 继承策略包版本与 Domain 基线）、写审计后即返回 `newRunId` —— **未接线到 2号位 主流程执行**。

对比白天候选路径（`CreateCandidateRunAsync`，同文件 `:526-527`）已完整接线：

```
CreateCandidateRunAsync → 新建 Candidate PlanVersion 壳（Status='Created'，VersionCategory='CANDIDATE'，SourceScheduleRunId=新 Run Id）
                        → _schedulingOrchestrator.RunSchedulingAndFinalizeAsync(...)   // RUNNING → COMPLETED / FAILED
```

恢复路径缺失的就是候选路径这段「壳 + 执行接线」，导致恢复 Run 空挂 RUNNING、永不真正重排，也无法收口。

---

## 二、阻塞根因（三处）

| # | 缺口 | 证据 |
|---|---|---|
| 1 | **恢复无 PlanVersion 壳** | `RecoverFailedRunAsync` 仅 `InsertForRecoveryAsync` 建 Run，未建 PlanVersion；而 `RunSchedulingAndFinalizeAsync` 需 `planVersionId` 作为 2号位 执行与结果写回目标 |
| 2 | **多域 vs 单域收口冲突** | FULL_SCHEDULE 恢复可能多 Domain，而 `RunSchedulingAndFinalizeAsync` 系「白天候选专用单域 + 单次收口」；逐域调用会**多次 `CompleteAsync`/`FailAsync` 同一 Run** |
| 3 | **恢复壳词表无归属裁决** | 恢复壳 `VersionCategory` / `Status` 语义属 2号位 执行词表，3号位 无既定裁决，不能自行定取值 |

## 三、请 2号位 裁定（三处，择定即收口）

1. **恢复收口 seam** —— 是否新增「按 Run 多域执行 + 一次性收口」接口，作为 FAILED 恢复专用执行 seam（区别于白天候选单域 seam）？还是复用既有 `RunSchedulingAndFinalizeAsync` 并扩展多域能力？
2. **恢复 PlanVersion 壳由谁建** —— 由 2号位 在执行侧建（3号位 仅传 `newRunId + Domain 基线`），还是由 3号位 在 `RecoverFailedRunAsync` 内仿候选壳先建（`Status='Created'`）再传入？
3. **恢复壳词表取值** —— `VersionCategory`（恢复路径取值，如 `RECOVERY` 或复用现有枚举）与 `Status`（建壳初值 + 收口终值）由 2号位 给出权威取值。

> 三处可分别裁定，3号位 侧按回执接线，S5/13 端点契约零改动。

---

## 四、影响范围

- **FAILED 运行无法端到端重跑**：恢复 Run 停在 RUNNING，无排程结果落库、无收口，P0-08 功能半程。
- **关联收口语义**：`IRunLifecycleService` 已定义的「被阻断判定」（Run 已终态且存在 FAILED 域时，无 PlanVersion 的预期域标记 BLOCKED）依赖恢复路径能真实回建 PlanVersion 壳。
- **依赖项**：跨版本排程连续性（`FirmFrozen`）、FULL_SCHEDULE 夜间 Run 的失败后恢复场景均依赖本接线闭环。
