## 一、已冻结审计一致性契约

| 项 | 契约 |
|---|---|
| 统一审计表 | `AuditLog`（DDL v1.3 收敛：治理/Candidate/运行/RBAC 审计统一写入 AuditLog，append-only） |
| 唯一入口 | `IAuditLogRepository`（Core 接口；Engine 实现为 EF Core + `AuthDbContext`） |
| 预检接口契约 | `IAuditLogRepository.EnsureWritableAsync` 接口文档即契约：「预检：确认审计库当前可写（开事务即回滚，不落数据），供治理写操作落库状态前调用」——即 F-G4 跨库一致性兜底 |
| 物理架构约束 | 治理 DML 落 **APS_Production**（`DatabaseConnectionManager` + Dapper）；审计落 **APS_Auth**（EF Core）。两库两连接，**无分布式事务（2PC/MSDTC）支持**——跨库原子性在架构上不可得 |

> 即：冻结契约**不承诺**「DML 与审计同一事务原子提交」（跨库物理上不可能），而是承诺「审计前置预检 + 业务后置追加」的一致性模式（下文补偿策略）。

## 二、失败补偿策略（fail-before-write）

**第一道防线 —— 审计前置预检（本次落码核心）：**
`EnsureWritableAsync` 先于一切治理 DML 调用（开 Auth 库事务并立即回滚，探测「可连接 + 可开写事务」）。审计库不可写 → 整操作失败、**业务零变更**——杜绝「已生效但无追溯审计」的规则/参数。

**残余窗口 —— 预检通过后、`AddAsync` 提交前审计库故障：**
跨库无 2PC，DML 已提交无法回滚。补偿 = `AddAsync` 异常向调用方传播（操作显式失败 500、可重试/人工核对），窗口已由预检最小化（毫秒级）。**本窗口如实文档化，不作虚假「原子回滚」宣称。**

**既有先例（P1-03 前已按本契约接入）：** `DomainDefinitionGovernanceService`（Create/Update/SetActive 3 处）、`RunLifecycleService`（1 处）。
