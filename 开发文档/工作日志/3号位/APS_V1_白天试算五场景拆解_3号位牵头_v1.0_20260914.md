## 〇、一句话结论

"白天试算"在系统里 = **白天候选运行（Candidate Run）**：以当前生效计划（ACTIVE 版本）为**只读基线**，算一版**候选（Candidate）**供人查看、对比、确认，确认后才可能采用（置生效（ACTIVE））。

所谓"5 种用法"，就是冻结在实施包 §十九里的 **5 条「运行类型（RunType）× 用途（Purpose）」合法组合**——不是 5 个接口、不是 5 个运行类型（RunType），而是同一条接口 `POST api/Governance/run/candidate` 上，由运行类型（RunType）+ 用途（Purpose）两个参数锁定出的 5 种业务语义。

| # | 场景名（业务问什么） | 运行类型（RunType） | 用途（Purpose） | 结果能否采用（激活） |
|---|---|---|---|---|
| ① | 能不能接单（可承诺量分析（CTP）） | 插单试排（INSERT_ORDER_WHATIF） | 可承诺量分析（CTP） | ❌ 永远只查看 |
| ② | 插单影响多大（插单影响分析（INSERT_IMPACT_ANALYSIS）） | 插单试排（INSERT_ORDER_WHATIF） | 插单影响分析（INSERT_IMPACT_ANALYSIS） | ❌ 永远只查看 |
| ③ | 局部插单重排（INSERT_RESCHEDULE） | 局部重排（LOCAL_RESCHEDULE） | 局部插单重排（INSERT_RESCHEDULE） | ✅ 确认后可采用 |
| ④ | 局部范围手工调整（MANUAL_ADJUSTMENT） | 局部重排（LOCAL_RESCHEDULE） | 手工调整（MANUAL_ADJUSTMENT） | ✅ 确认后可采用 |
| ⑤ | 域级手工调整重排 | 手动重排（MANUAL_RESCHEDULE） | 手工调整（MANUAL_ADJUSTMENT） | ✅ 确认后可采用 |

> 关键分界：**①② 是"预演/问诊"，结果只读、永不落地**；**③④⑤ 是"试排/调整"，先算候选、人确认后才激活生效**。这是同一套候选机制下的两个家族，不能混为一谈。

## 一、先定术语，避免继续"一个词、五个义"

- **白天候选运行（Candidate Run）**：排程运行（ScheduleRun）表中 `运行类型（RunType）∈ {手动重排（MANUAL_RESCHEDULE）, 局部重排（LOCAL_RESCHEDULE）, 插单试排（INSERT_ORDER_WHATIF）}` 的一次白天运行记录。区别于夜间全量批排程（全量排程（FULL_SCHEDULE））。
- **用途（Purpose）**：对同一类运行，"这次算完到底回答哪个业务问题"。4 个可用值：可承诺量分析（CTP）/ 插单影响分析（INSERT_IMPACT_ANALYSIS）/ 局部插单重排（INSERT_RESCHEDULE）/ 手工调整（MANUAL_ADJUSTMENT）。
- **基线版本（Base PlanVersion）**：白天候选所锚定的当前生效（ACTIVE）计划版本（PlanVersion），**只读、不改**，候选在其上算。
- **候选壳（Candidate PlanVersion）**：版本类别（VersionCategory）= 候选（CANDIDATE）的计划版本（PlanVersion）壳，承载候选结果；状态（Status）走执行词表 `已创建（Created）→ 计算中（Computing）→ 已算完（Computed）/ 计算失败（ComputeFailed）`，被采用时置生效（ACTIVE）（治理动作）。
- **采用 / 激活（Activate）**：把候选置为域内唯一生效（ACTIVE），同域旧生效（ACTIVE）归档为归档（ARCHIVED）。①② 两类**被硬性禁止**走到这一步。

> 注：运行类型（RunType）里的模拟（SIMULATION）字面量与"白天试算"**不是一回事**——它不属于白天候选类（候选创建直接拒绝模拟（SIMULATION）），本拆解不覆盖它。若 0号位 希望把模拟（SIMULATION）也纳入"试算"排点，需另行裁定。

## 二、两个家族（先分清楚，再看五个）

### 家族 A：预演/问诊（①②）——只回答"假如"，绝不改计划

- 触发人：跟单/销售/计划员面对"能不能接这单、插进去会怎样"这类**即时提问**。
- 语义：把"一张新订单"当成虚拟输入，在只读基线上排一版，得到回答后即弃——**结果只查看、不可确认、不可激活**（代码硬校验：插单试排（INSERT_ORDER_WHATIF）的候选来源运行（Run）永远不得激活，`RunLifecycleService.EnsureSourceRunActivatableAsync`）。
- 共同缺口：**"新订单从哪里进"在需求源头就是空的**（见 §五 待决 1）。

### 家族 B：试排/调整（③④⑤）——先算候选，人确认后落地

- 触发人：计划员要调整正式计划（局部或全量），先把调整算成候选，看清楚效果，**确认**后才替换生效计划。
- 语义：以基线订单算一版候选，候选 → 人工确认 → 生效（ACTIVE）。
- 与家族 A 的本质区别：**有"采用"这道门，且必须人工确认（候选确认（ConfirmCandidate）审计是激活硬前置）**。

## 三、逐场景拆解

### 场景 ①｜能不能接单（可承诺量分析（CTP））

| 维度 | 说明 |
|---|---|
| 运行类型（RunType）× 用途（Purpose） | 插单试排（INSERT_ORDER_WHATIF）× 可承诺量分析（CTP） |
| 业务问题 | 客户问"这单 X 量、Y 交期，能不能接、最早什么时候交？" |
| 输入 | 只读基线 + **一张待评估的新订单**（含数量、期望交期） |
| 计算语义 | 在基线上把新单当成虚拟需求，正排产能/物料，回答"可承接的可行交期" |
| 输出 | 一个候选结论（交期/产能可行性），供查看、对客户报价/承诺 |
| 能否采用 | ❌ **永远不可采用**（结果只用于答复，不落正式计划） |
| 权限 | V1 功能权限须覆盖可承诺量分析（CTP）；审计记录可承诺量分析（CTP） |
| 现状 | 候选机制已建，但**新订单装载缺口未解**（§五 待决 1）——当前无法真正跑出"能不能接单" |

### 场景 ②｜插单影响多大（插单影响分析（INSERT_IMPACT_ANALYSIS））

| 维度 | 说明 |
|---|---|
| 运行类型（RunType）× 用途（Purpose） | 插单试排（INSERT_ORDER_WHATIF）× 插单影响分析（INSERT_IMPACT_ANALYSIS） |
| 业务问题 | "把这张新单插进去，会挤掉谁、延误多少、产能冲突多大？" |
| 输入 | 只读基线 + **一张待评估的新订单** |
| 计算语义 | 在基线上插入新单，量化对现有订单交期、产能负荷的扰动 |
| 输出 | 影响分析结论（哪些单被推后、延误量、瓶颈资源冲突），供决策是否接单/如何插 |
| 能否采用 | ❌ **永远不可采用** |
| 权限 | V1 功能权限须覆盖插单影响分析（INSERT_IMPACT_ANALYSIS）；审计记录插单影响分析（INSERT_IMPACT_ANALYSIS） |
| 现状 | 同上，新订单缺口未解；**插单语义本身也待 0号位 定**（§五 待决 2） |

### 场景 ③｜局部插单重排（INSERT_RESCHEDULE）

| 维度 | 说明 |
|---|---|
| 运行类型（RunType）× 用途（Purpose） | 局部重排（LOCAL_RESCHEDULE）× 局部插单重排（INSERT_RESCHEDULE） |
| 业务问题 | "有单要插，但想只重排受影响的局部，别把全局打乱" |
| 输入 | 只读基线 + 新订单（进入候选），重排范围限定在**局部/相关域** |
| 计算语义 | 局部范围内插入并重排，冻结区尽量不动 |
| 输出 | 候选结果（局部新排程），查看 → 确认 |
| 能否采用 | ✅ **确认后可采用**（候选确认（ConfirmCandidate）→ 激活置生效（ACTIVE）） |
| 权限 | V1 功能权限须覆盖局部重排（LOCAL_RESCHEDULE）；审计记录局部重排（LOCAL_RESCHEDULE）及确认/激活 |
| 现状 | 候选机制可用；但"局部范围如何界定、新订单是否含在内"依赖 §五 待决 1/2 的口径 |

### 场景 ④｜局部范围手工调整（MANUAL_ADJUSTMENT）

| 维度 | 说明 |
|---|---|
| 运行类型（RunType）× 用途（Purpose） | 局部重排（LOCAL_RESCHEDULE）× 手工调整（MANUAL_ADJUSTMENT） |
| 业务问题 | "不动全量，只对某个局部（某产线/某批单）做手工微调" |
| 输入 | 只读基线 + 针对局部的手工调整意图（非插单触发） |
| 计算语义 | 局部重排，体现手工调整 |
| 输出 | 候选结果 → 确认 → 采用 |
| 能否采用 | ✅ **确认后可采用** |
| 权限 | V1 功能权限须覆盖局部重排（LOCAL_RESCHEDULE）；审计记录局部重排（LOCAL_RESCHEDULE） |
| 现状 | 候选机制可用；与 ③ 的边界（插单触发 vs 手工触发）需 0号位 一句话口径固化（§五 待决 3） |

### 场景 ⑤｜域级手工调整重排

| 维度 | 说明 |
|---|---|
| 运行类型（RunType）× 用途（Purpose） | 手动重排（MANUAL_RESCHEDULE）× 手工调整（MANUAL_ADJUSTMENT） |
| 业务问题 | "换规则/换参数/手工改约束，把整个（单）域重排一版，看新版效果后正式替换" |
| 输入 | 只读基线 + 新的规则/参数/手工调整（严格单域，预期域清单（ExpectedDomainKeysJson）=[域 D1]） |
| 计算语义 | 在只读基线上按新策略重算一版域级候选 |
| 输出 | 候选结果 → 人工确认 → 生效（ACTIVE）替换同域旧生效（ACTIVE）（旧版本归档归档（ARCHIVED）） |
| 能否采用 | ✅ **确认后可采用** |
| 权限 | V1 功能权限须覆盖手动重排（MANUAL_RESCHEDULE）；审计记录手动重排（MANUAL_RESCHEDULE）、确认/激活 |
| 现状 | 候选机制最完备的一条；触发契约（方案 A）与执行侧基线快照保护已提交 2号位（§五 待决 5） |

## 四、五场景共性的硬约束（不管哪一条都成立）

1. **基线只读**：候选一律以创建时冻结的基线版本标识（BasePlanVersionId）指向的生效（ACTIVE）版本为只读基线，**不修改基线**，候选壳只承载结果。
2. **严格单域**：白天候选预期域清单（ExpectedDomainKeysJson）冻结为单域（如 `["域 D1"]`），只算一个域。
3. **创建时冻结三要素**：运行类型（RunType）× 用途（Purpose）× 默认策略包版本，创建瞬间锁定，缺省取当前生效（ACTIVE）；默认策略版本缺失或歧义一律拒绝（红线 #4，不盲目取第一个）。
4. **候选不自动生效**：任何候选都需走 `已创建（Created）→ 计算中（Computing）→ 已算完（Computed）`，且 **①② 到已算完（Computed）即止**；③④⑤ 还需候选确认（ConfirmCandidate）人工确认 → 激活（Activate）。
5. **全程审计**：创建候选运行（CreateCandidateRun）、候选确认（ConfirmCandidate）、激活（Activate）均写 Auth 库治理审计日志（GovernanceAuditLog），追溯"谁、何时、用哪个基线、算哪一域、什么用途"。
