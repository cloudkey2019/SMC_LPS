## 一、前因后果（5 分钟读完）

**为什么会有这件事——来自 4号位 联调：**

4号位 `/rules` 页面（页面10 规则、参数与策略维护）在联调时，计划在规则集列表卡片上展示**所属域标签（Domain tag）**，据此请求 `GET /api/governance/rule-sets` 列表 DTO 新增 **`DomainKey`** 字段（催办单 R2，P1）。

3号位 在 R2 实施前逐项核查线上库（`APS_Production` 10.116.2.75，v5.1.8.2 schema）与代码，核心发现是一个**数据模型层面**的问题，不是一个简单补字段能解决的。

**为什么不能直接补字段 —— 三层核查证据：**

| 核查层 | 结果 |
|---|---|
| `RuleSetVersion` 全列 | 无 `DemandDomainKey` 列（催办单假设的来源列在线上不存在）|
| `RuleSet` 主表全列 | 无任何域相关列 |
| 全库扫 `DomainKey`/`DomainId` | 仅命中 `DomainDefinition`（域字典）/ `Order` / `PlanVersion` 3 张表 —— **全是排程/版本级**，规则集三张治理表全无 |
| 扫描规则集↔域关联表 | 空，无任何中间/关联表 |
| 代码层搜 `RuleSet.*Domain` / `Domain.*RuleSet` | 零命中，无关联机制 |
| 冻结文档 v1.4 §十八（页面10 契约源头）| DomainKey 全在 **PlanVersion/Order** 上下文，**页面10 不提域** |

**结论一句话：**

> **规则集在数据模型上不存在「域」这一维度。** DomainKey 是 **PlanVersion（计划版本）/ Order（订单）级**概念——标识「某次排程 / 某订单属于哪个业务域」；而规则集是**全局治理对象**（一套规则配置可被任意域引用）。4号位 卡片 Domain tag 需求背后是**模型层缺失**，而非字段缺失。

## 二、为什么 3号位 不能自行定案（不越权理由）

按 **方案A 已裁决的真相源原则**（P0-01/P0-02）：规则集内容以 `ContentSnapshotJson` 单列为唯一真相源，不能随意造字段。若给 DTO 硬加 `DomainKey`，三条路全是错：

| 做法 | 后果 |
|---|---|
| 恒返回 `null` | 前端 Domain tag 永远空白，**契约失真**（前端以为有值）|
| 从 `DemandDomainKey` 取 | **列不存在**，SQL 直接报错 |
| 从 `DomainDefinition` 猜 | **猜测无依据**，违反红线 #4「物料映射禁止盲目 First()」精神；业务上错误——规则集本就不属于某域 |

→ **「是否给规则集引入域维度」是架构/业务决策**（影响是否要 DDL、是否改动数据模型），按号位职责归 **0号位** 裁决，3号位 不自作主张。这正是原提请函的原因，本函重申。

### 提请 1：规则集是否需要「所属域」维度？

### 提请 2（若提请 1 裁 b）域关联机制选项

| 选项 | 机制 | 实施方 | 影响 |
|---|---|---|---|
| a | `RuleSetVersion` 加 `DomainKey` 列（版本级域，随版本发布固化）| 2号位 DDL + 3号位 治理 | 版本级隔离，需 DDL 变更申请 |

| c | `ContentSnapshotJson` 内嵌域字段 | 3号位 治理（无 DDL）| 零 DDL，但域语义混入内容快照，与「快照=可重放内容」定位冲突 |
