## 一、背景

当前 5号位对外的 11 个只读查询 Controller 全部用同一个权限码 `aps.plan.view` 做类级 `[Authorize]`。这是 2026-09-12 的**临时安全堵漏**——当时这 11 个 Controller 完全裸奔（无任何鉴权），先统一加 PlanView 防越权。

0号位 31-0 裁决明确：**"不能永久归成 `aps.plan.view`，正式按业务动作用对应权限。"**

## 三、需要 3号位做的事

### 3.1 定义并注册权限码

在 `PermissionCodes` 和 `APS_Auth.Permission` 表中，为上述 9 个查询接口新增对应的查看权限码（`*.view`）。建议命名规范：

```
aps.issue.view
aps.domain_status.view
aps.explanation.view
aps.governance.view
aps.overview.view
aps.pegging_trace.view
aps.pi_position.view
aps.supply_trace.view
aps.order.view
aps.demand_protection.view
```

### 3.2 分配角色

按角色职责分配：
- **PMC**（计划员角色）：全部查看权限
- **VIEWER**（只读角色）：全部查看权限（或按业务需要裁剪）
- **ADMIN**：全部

### 3.3 5号位配合

3号位完成权限码注册 + 角色分配后，5号位当天可批量切换 Controller 的 `[Authorize(Policy = ...)]`（每个 Controller 改一行，零风险）。

## 四、时间期望

| 项 | 期望 | 说明 |
|---|---|---|
| 3号位注册权限码 + 分配角色 | 2026-09-25 前 | 5号位 11 个 Controller 改 `[Authorize]` 属性即可，无业务逻辑改动 |
| 5号位切换 | 权限码就绪后当天 | 每个 Controller 只改类级 `[Authorize]` 一行 |

## 五、当前不阻塞

`aps.plan.view` 是 5 角色均持有的权限码，**不会误拦任何合法用户**，只是粒度不够细（功能权限是粗放的"能看排程就能看所有"）。正式上线前分细化即可，不构成 P0 安全风险。
