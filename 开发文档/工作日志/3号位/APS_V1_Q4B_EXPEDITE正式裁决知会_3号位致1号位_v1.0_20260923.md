## 一、终裁一句话（转载 0号位 首页八）

> **EXPEDITE 表示用户指定需求订单进入加急优先模式。在白天 Candidate 重排中，系统调整需求订单优先级，允许 EXPEDITE 需求与当前计划中的可调整需求重新竞争资源，并在新的需求排序基础上重新执行 Pegging 和排程。EXPEDITE 不能突破已形成执行事实、业务保护约束以及物料、资源、工艺等硬约束。V1 不自动计算牺牲成本，仅输出影响范围供业务确认。**

---

## 二、调整对象与链路（Solver 落地要点）

- 调整对象 = **需求订单（Demand）**，非 Task；不采用直接移动 Task 的插单逻辑。
- 链路：

```
需求订单优先级调整 → 重新 Demand 排序 → 重新 Pegging → 重新生成 Task → 重新有限产能排程
```

- **不可插入 ≠ 不参与 Candidate**：受保护订单仍作为输入存在，仅 EXPEDITE 不能强行改变其保护优先级/执行约束。

## 三、三类不可突破约束（Solver 落点）

| 保护边界 | Solver 落实 |
|---|---|
| ① 执行事实 | 已完工/已开工/已领料 → 不重排 |
| ② 业务保护 | Firm/Frozen、已确认不可调整 → 不抢占保护位置 |
| ③ 技术硬约束 | 物料 AvailableTime / 资源日历 / Routing / 有限产能 → 必须满足 |

## 四、落码边界（与 2号位 S5 一致性）

2号位 已按终版口径落地 Demand 层「EXPEDITE 前置竞争层」（`UpstreamDemand.OrderCanonicalId`，命中集合作独立桶整体前置、桶内走冻结 `DemandPriorityConfig` 排序、非恒先、不新增 Task 优先级、不突破硬约束）。**Solver 侧不应再重复实现一把 EXPEDITE 硬优先级**——竞争力/排序语义由 Demand 层供给，Solver 原有限产能逻辑不需感知 EXPEDITE 特判。
