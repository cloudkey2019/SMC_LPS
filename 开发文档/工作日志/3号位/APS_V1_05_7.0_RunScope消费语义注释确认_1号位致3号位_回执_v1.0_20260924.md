## 二、④A 需调整：与**冻结 v1.7 §69/§70** 直接冲突（本件核心）

### 2.1 贵方 ④A 原稿

> `RunScope == null` 或本集合为空 → **全 Domain 可移动**（现状不变）；非空 → 集合内需求 = **Anchor 可移动范围**、补集 = **不可移动真实约束**（占资源/时间、不参与重排）。

### 2.2 冻结基线原文（PM 冻结文档 20260921，最新权威）

**《APS_V1_最终全部流程与业务基线_v1.7_…完整合并版.md》§69（`:1614`）**：

> ## 69. 影响范围由1号位动态判断
> 2号位先把本次一个业务场景中的一个或多个同类型对象转换为变化Seed；**1号位从这些Seed开始传播**。
> 变化Seed可以是：新增/变化的LogicalProductionDemand；一个或多个Task软目标；一台或多台故障Resource；一台或多台Calendar变化Resource。
> **Seed只决定传播起点，不限制Solver读取当前完整真实上下文。**
> 不按：产品族；固定7天/14天；固定订单数。**硬截断。**

**同文 §70（`:1642-1652`）**：

> ## 70. 待检查队列（Dirty/Affected Queue）
> …**这是1号位固定算法，不进入规则引擎。**

**同文 第十七部分前段（`:1605-1610`）**：

> Scope外Task：**不得被本次Candidate移动**；**仍作为真实资源/时间占用进入Solver。**

### 2.3 冲突点

| 维度 | 冻结 §69/§70 | 贵方 ④A 原稿 |
|---|---|---|
| 可移动范围**由谁定** | **1号位 从 Seed 传播动态推导**（§69 标题原文）| 投影侧传入的 `InScopeLogicalDemandKeys` 集合 |
| 算法归属 | **1号位 固定算法，不进入规则引擎**（§70 明文）| 被替换为「投影侧集合切分」 |
| Seed 的角色 | 「只决定传播起点，**不限制** Solver 读取当前完整真实上下文」| 集合外 = 不可移动（等价于对可移动域做集合**硬截断**，与 §69「不按…硬截断」反向）|

**贵方 ④A 的第二句是对的**——「补集 = 不可移动真实约束（占资源/时间）」正是 §69 段末「Scope外Task 不得被移动、仍作为真实资源/时间占用进入 Solver」。这部分**1号位 完全认可**，也不与本方冲突。

**冲突只在第一句**：可移动范围的**来源**。④A 把它从「1号位 Seed 传播推导」搬到了「投影侧集合」，这**实质修订了 §69/§70**。

### 2.4 投影侧实现现状：恒空 → ④A 会把局部重排架空

- **Core 头注**（`LPS.APS.Core/Dto/DomainSolveRequest.cs:75-76`，归 2号位）：
  > `InScopeLogicalDemandKeys` 按冻结 v1.7 §69 留空：**影响范围由 1号位 从变化 Seed 动态传播推导**，2号位 只转 `ChangeSeed`/`TaskTarget`/`ChangedResourceIds`（**不预填可移动集合** / Scope 外 Anchor·Block）。

- **投影侧代码**（2号位，`LPS.APS.Application/Services/PeggingOrchestrator.cs:4669`）：
  ```csharp
  InScopeLogicalDemandKeys = Array.Empty<string>(),  // 冻结 v1.7 §69：影响范围由 1号位 从变化 Seed 动态传播推导；
                                                     // 2号位 只转 ChangeSeed/TaskTarget/ChangedResourceIds，不预填可移动集合
  ```
  —— **恒为空数组，无任何填充路径。**

**推论**：若 ④A 照稿落进契约，则必然读到「空 → 全 Domain 可移动」→ **每次 Candidate 都退化为全 Domain 重排**，与冻结 §72《局部重排工程默认值》（`:1664-1676`：正常 Candidate 60s / 软预算 90s / 局部硬预算 180s / 受影响 Task 比例阈值 30%）**在工程定位上互相打脸**：那个预算表只有在「局部」成立时才有意义，而 §73《LOCAL 的单 Domain 完整重排兜底》（`:1680`）明确定位「完整重排」是**影响范围太大时的兜底**，不是常态。

### 2.5 1号位 当前实际消费语义（供落稿引用）

`InScopeLogicalDemandKeys` **1号位 零消费**（`LPS.APS.Scheduling` 全层 0 命中）。可移动范围的**实际**推导入口是 `CandidateContext.ChangeSeedKeys`：

——**这正是 §69/§70 要的形状**，且与 Core 头注、2号位 投影侧三方可自洽。
