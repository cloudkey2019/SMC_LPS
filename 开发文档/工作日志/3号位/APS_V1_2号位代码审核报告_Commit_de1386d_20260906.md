# 四、P0——必须先关闭的冻结冲突

# P0-01 `ExecuteBatchPeggingWorkflowAsync` 按20单切批，破坏整个 Domain 的数量真相、优先级、Solver真相和事务真相

## 代码事实

当前：

```csharp
const int batchSize = 20;
foreach (var batch in request.OrderIds.Chunk(batchSize))
{
    ...
    results.Add(await ExecutePeggingWorkflowAsync(batchRequest, ...));
}
```

而每一个 `ExecutePeggingWorkflowAsync` 都会重新：

1. 装载完整 `SupplyPool`；
2. 从 `NextAllocationSequence = 1` 开始；
3. 独立执行 Demand Priority；
4. 独立执行 Pegging；
5. 独立调用一次 Solver；
6. 独立开启一次持久化事务。

## 冻结冲突

当前冻结业务要求：

> **一个 Domain 是一个独立 Pegging / Solver / PlanVersion 数量与时间真相边界。**

20单切批后会出现四个直接错误：

### A. Supply重复消费

第1批扣掉的 Inventory / PI / PO / VMI 只存在第1批内存 `SupplyPool`。

第2批重新从数据库装载原始数量，代码没有按前批已落 `PeggingSupplyAllocation` 回扣供给。

因此同一物理 Supply 可能被多个批次重复分配。

### B. Demand Priority只在20单内部成立

全 Domain 高优先级订单可能落在后一个 Chunk，却无法与前20单竞争同一供给。

这破坏冻结的 Domain 内 Demand排序权威。

### C. 一个 Domain 被多次独立调用 Solver

不同 Chunk 的 FinalTask 无法在同一个有限产能问题中竞争、合批、拆批和优化。

这直接违反：

> **每个 Domain 一个完整有限产能问题。**

### D. AllocationSequence 会从1重复开始

`PeggingResult.NextAllocationSequence` 默认值为1，而 DDL 已冻结：

```text
UNIQUE (PlanVersionId, AllocationSequence)
```

第二个批次若存在非Task Allocation，会与前一批 AllocationSequence 冲突。

## 事务问题

文档要求：

> **单Domain事务统一持久化。**

现在只是：

> **单20单批次事务。**

如果第1批已提交、第2批失败，会留下一个 `ComputeFailed` PlanVersion 内的部分正式结果。

## 裁定

> **P0。必须修改。**

## 最小整改方向

不是重写 Pegging。

应保留当前内存结构，把“20单Chunk”从**业务真相切分**改成：

- 数据加载批处理 / SQL分页 / 内存性能手段可以保留；
- 但一个 Domain 必须共享同一 Demand排序结果、同一 SupplyBalance、同一 AllocationSequence、同一 LogicalProductionDemand 集合；
- 只调用一次 Domain Solver；
- 按单Domain事务统一持久化。

# P0-02 PI Position 正在反向修改 ProductionInstruction Supply 数量

## 代码事实

当前注释和代码明确：

```text
located → 入SupplyPool
unlocated → 不入池，转新增生产
```

实际：

```csharp
locatedQty = Positions.Where(!IsUnlocated).Sum(...)
availableQty = Min(erpRemainingQty, locatedQty)
```

如果全部 UNLOCATED：

```csharp
continue;
```

即该 PI 整体不作为 Supply。

## 冻结业务

当前冻结已经明确：

> ProductionInstruction 本身仍是 Supply。

> Position 只是 PI 内部“在哪里”的解释。

> Position 不得替代 PI Supply，不得重新计算 PI 总剩余数量。

即使 Position 无法定位：

> **PI 仍可按 ERP RemainingQty 作为 PI Supply 被承接，只是执行起点降级为 UNLOCATED 保守处理。**

## 当前风险

例如 ERP PI RemainingQty=1000：

- Position定位800；
- UNLOCATED=200；

当前代码只把800作为PI/WIP Supply。

剩下200会落入 `NEW_REQUIREMENT`，等于：

> 原有PI还有200未完成，却又新增生产200。

这是典型重复生产风险。

## 裁定

> **P0。Supply / Position核心边界冲突。**

## 最小整改方向

- PI Supply数量始终以 ERP RemainingQty 为权威；
- Position只用于承接PI后内部数量份额解释；
- UNLOCATED仍属于该PI；
- 不用 Position sum 反向裁剪 PI Supply。

# P0-03 90天有限产能求解边界被错误压缩成“当前时间+2小时”

## 代码事实

`BuildPeggingRequest`：

```csharp

FrozenWindowEnd = now.AddHours(2)
```

随后 `DomainSolveRequest`：

```csharp

PlanningEnd = request.FrozenWindowEnd
```

因此 1号位收到的正式：

```text

```

而不是当前 PlanVersion 的90天 Horizon。

同时，ScheduleRun 已有冻结 `DataCutoffTime`，但 Pegging 又重新使用 `DateTime.Now`。

## 冻结业务

V1要求：

- 90天滚动窗口全部进入一套有限产能 Solver；
- `DataCutoffTime` 属于本Run冻结事实时间；
- Firm/Frozen 是约束，不是 Solver Horizon。

## 当前问题

代码把：

> “2小时冻结窗口”

误当成了：

> “Solver PlanningEnd”。

这会直接使 `DomainSolveRequest` 的求解边界与90天正式计划冲突。

## 裁定

> **P0。**

## 最小整改方向

必须分离三个概念：

1. `DataCutoffTime`：ScheduleRun冻结事实时点；
2. `HorizonStart/HorizonEnd`：PlanVersion正式90天边界；
3. Firm/Frozen窗口：作为 Execution/Immovable Constraint 传给1号位。

禁止再用 FrozenWindowEnd 充当 PlanningEnd。
