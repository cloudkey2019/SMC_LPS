# 三、RELEASED工单：先纠正1号位、2号位当前的一个倾向

1号位、2号位都倾向：

> `RELEASED`已有MES工单，因此应直接归B桶，复用该MES工单，不再重排Batch。

这个建议**目前不能直接接受**。

原因不是技术，而是它与当前冻结业务存在明确冲突。

当前正式冻结口径仍是：

```text
RELEASED = 待开工
IN_PROGRESS = 已开工未完成
CLOSED = 已完成
DELETED = 已删除
```

并且已经明确：

> `RELEASED`不形成执行连续；只有`IN_PROGRESS`在存在当前有效Q时形成执行连续份额。

跨版本连续性冻结也已经明确：

> 未开工MES工单不继承MES执行身份；原则上旧工单删除/作废后，根据最新生产真相重新排程并生成新的TaskNo / MES工单。

因此：

> **不能因为当前下发/撤销链路尚未做完整，就为了避免重复建单而把RELEASED改成B桶。**

这违反了本项目一直坚持的原则：

> 不能为了保护代码或当前实现方便而静默修改冻结业务。

# 四、RELEASED真正暴露的问题是什么

`RELEASED`实测有8万多张，这不是证明“RELEASED应该继承”。

它证明的是：

> **当前“未开工MES工单撤销/作废/重建”的下发生命周期没有闭环。**

也就是：

```text
上一版本存在RELEASED MES工单
↓
下一FULL重新形成当前Q
↓
该工单不作为已执行连续份额
↓
当前计划重新决定Batch / TaskNo
↓
正式创建新MES工单之前
必须先确认旧RELEASED工单已经作废/撤销
↓
再创建新工单
```

如果这一步没有做：

```text
旧RELEASED仍存在
+
新TaskNo继续下发
```

当然会造成重复工单。

所以这里真正需要补的是：

> **MES下发对账 / 旧RELEASED工单撤销闭环。**

而不是直接改变A/B/C冻结定义。

# 七、因此那14条Task应该收敛成几个TaskNo？

这里要区分“历史错误数据”和“下一版正确结果”。

当前：

```text
1张RELEASED MES工单
14条Task
14个TaskNo
```

这组历史数据本身是不合规的：

- TaskNo粒度错；
- Operation拆批机械均分；
- 一个MES工单被APS拆出多个TaskNo。

但是，因为该MES工单是`RELEASED`，按当前冻结业务：

> 下一FULL不应该简单把14个TaskNo“收成1个TaskNo然后继续旧WO”。

正确逻辑是：

```text
旧RELEASED工单
→ 进入“待撤销/待作废”下发对账
→ 当前Q重新进入C类自由求解
→ 1号位按新Batch Policy重新决定Execution Batch
→ 2号位按ExecutionBatchKey生成新的TaskNo
→ 旧MES工单成功作废后，才允许新MES工单创建
```

因此：

> **下一版到底形成1个还是多个TaskNo，应由1号位新的Batch Decision决定。**

不能从“旧MES只有一张工单”直接推导“新计划也必须一张”。

如果当前业务最终确认RELEASED不可撤销，那才会变成：

```text
一张RELEASED WO
→ 一个TaskNo
→ N条Operation Task
```

这是另一项业务裁决，不能现在混在一起。

# 十一、Q-1：排不下时向后搜索的终止边界

这项本轮也可以裁掉，不需要让1号位三选一。

正式规则：

## 11.1 DueDate / PlanningEnd / 90天窗口不是硬终止边界

如果PlanningEnd以后仍然存在**正式Resource Calendar中的合法产能**：

```text
PlanningEnd=9/30
10/3存在真实合法Calendar Slot
```

则：

```text
Task可以排到10/3
```

并记录：

```text
延期
+
超计划窗口
```

不能因为超过PlanningEnd直接变成Unscheduled。

## 11.2 但不允许制造虚拟无限产能

V1不恢复：

```text
Calendar结束后
→ 自动生成7×24虚拟日历
```

也不采用：

```text
低置信虚拟Capacity Slot
```

作为正式计划。

因为：

> 没有真实日历，就不能说“未来仍存在合法产能”。

## 11.3 1号位的可证明搜索边界

定义为：

> **本次ScheduleRun已加载的相关Eligible Resource正式Calendar最晚有效时间。**

在这个时间之前：

- 只要有合法槽，就必须继续找；
- DueDate / PlanningEnd不截断。

如果直到正式Calendar末端仍找不到：

返回：

```text
CALENDAR_COVERAGE_INSUFFICIENT
```

或现有等价Issue。

其业务含义是：

> 日历覆盖范围不足，APS无法证明更远未来的合法产能。

这不是：

```text
真实产能一定不存在
```

也不是：

```text
普通延期
```

## 11.4 运维要求

资源日历必须覆盖：

```text
90天正式计划窗口
+
足够的向后搜索缓冲区
```

具体是180天、365天或其它范围，作为运维/参数要求，不硬编码进Solver。

测试数据可先准备365天。

# 十八、1号位修正一：强制Max拆批不能被“最多3批”截断

1号位当前方案中存在：

```text
FreeQty > Max
→ ceil(Q/Max)
→ 批次数最多3
```

这不成立。

硬Max是硬约束。

例如：

```text
Q=10000
Max=1000
```

必须至少：

```text
10批
```

不能因为V1优化搜索只考虑2/3批，就生成3个超Max Batch。

正式区分：

## 强制拆批

为了满足硬Max：

> 需要几批就必须几批。

不受：

```text
MaxOptimizationSplitCount
MaxBatchCandidates
```

限制。

## 优化性拆批

为了改善交付/库存/资源/Setup：

才受：

```text
MaxOptimizationSplitCount
MaxBatchCandidates
```

约束。

# 十九、1号位修正二：强制Min/Max先求合法批数区间

给定：

```text
总量 Q
最小批量 Min
最大批量 Max
```

合法批次数n必须满足：

```text
ceil(Q / Max) <= n <= floor(Q / Min)
```

如果不存在合法n：

```text
BATCH_POLICY_CONFLICT
```

例如：

```text
Q=1100
Min=600
Max=1000
```

至少需要2批；
但2批每批至少600，总计至少1200。

无合法分法。

此时禁止：

- 550+550；
- 偷偷降低Min；
- 1100整批；
- 只排1000剩100。

必须显式暴露业务规则冲突。

# 二十、1号位修正三：WholeBatch超时回退有前提

→ WholeBatch

WholeBatch已经非法，不能作为fallback。

正确层级：

```text
硬约束合法基础方案
→ 永远必须形成

优化候选
→ 可以超时放弃
```

所以：

- 强制Max拆分不能因为超时取消；
- 优化性拆批可以降级到“硬约束合法的基础方案”。

# 二十一、1号位修正四：优化性三批不能重新机械均分

1号位当前仍有：

```text
严重延期
→ 三批均分候选
```

这会把旧均分算法换个入口带回来。

优化性切点必须来自：

- 高保护需求累计断点；
- PreferredBatchQty附近；
- 资源竞争释放点；
- Min/Max合法边界。

如果最终恰好接近三等分可以接受。

但：

> **“三等分”不能是候选产生原因。**

# 二十二、强制Max拆分可以“均衡分配”，但含义不同

例如：

```text
Q=2100
Min=500
Max=1000
```

硬Max决定至少3批。

此时可以构造一个合法基础方案：

```text
700 + 700 + 700
```

这里的均衡分配只是：

> 在硬规则已经确定必须3批以后，构造一个稳定、合法的基础分区。

它与旧逻辑：

```text
优化性2批=50/50
优化性3批=1/3
```

不是同一件事。

代码命名必须区分。

# 二十三、1号位修正五：DemandGoalType与对象血缘分开

1号位当前建议：

```text
RootDemandType
= CUSTOMER / INVENTORY / INTERPLANT / ORPHAN
```

这会重新把“对象类型”带回正倒排方向。

不采用。

建议：

## DemandGoalType

只表达真正保障目标：

```text
CUSTOMER_COMMITMENT
INVENTORY_REPLENISHMENT
```

## Source / Lineage

另外保留：

```text
SALES_ORDER
MTS
INTERPLANT
...
```

用于解释和追溯。

跨厂对象：

```text
INTERPLANT
```

本身不能直接决定Forward/Backward。

必须看它最终服务：

- 客户承诺；
- 上层MTS；
- 目标工厂库存补充。

# 二十四、ProtectionLevel与BusinessPriority不要形成两套真相

建议2号位给1号位时收敛为：

```text
ProtectionTier
+
PrioritySequence
```

其中：

### ProtectionTier

表示：

- 执行连续；
- Demand Protection；
- 客户承诺；
- 其它业务保护层级；

的归一结果。

### PrioritySequence

只做同层稳定排序。

不要给1号位两个彼此独立的：

```text
ProtectionLevel
BusinessPriority
```

再让1号位决定哪个更大。

# 二十五、正倒排：RELEASED问题暂时不能改变现有算法分桶

只适用于真正的：

IN_PROGRESS连续份额
```

如果未来0号位重新打开RELEASED业务并决定“工单创建即固定Batch身份”，再单独增加：

```

本轮先不提前落这条新业务。

# 二十六、1号位修正六：Phase5可以复用“字典序框架”，不能原样复用现有具体条件

1号位认为：

```text
不新增延期
+
总延期不升
+
Setup严格下降
```

已经等于新的目标层级。

不完全正确。

例如：

```text
方案A：
高保护客户延期
Setup少

方案B：
高保护客户按期
Setup多一次
```

新冻结必须选方案B。

所以阶段A最终Comparator必须按：

```text
1. Hard Constraint
2. Demand Protection / ProtectionTier
3. Customer Commitment
4. Inventory Protection
5. Total Tardiness / Setup / WIP / Stability
```

排序。

可以复用：

> 字典序、硬门控、不使用巨大加权总分。

不能原样保留：

> “Setup必须严格下降才接受”的旧条件。

---

# 二十七、1号位修正七：性能策略不要变成“每个C需求×6次完整Phase2”

不采用：

```text
每个C桶Demand
→ 最多6个候选
→ 每个候选跑完整Phase2
```

再把多Demand候选做组合。

这在10万Task规模下风险太大。

V1推荐：

```text
1. 先形成硬约束合法基础Batch
2. 全Domain跑一次初始排程
3. Phase3诊断
4. 只对真正命中问题的少量Batch生成优化候选
5. 复用Phase4影响集做局部重排
6. 严格改善才接受
7. 有界迭代
8. 必要时单Domain完整重排兜底
```

这样：

- 不做候选笛卡尔组合；
- 大多数正常Batch只跑一次；
- Batch Adjustment真正变成“诊断驱动局部优化”。

这更符合现有Solver骨架，也更符合15分钟性能目标。

---

# 二十八、Merge与Execution Batch归组必须彻底分开

1号位已经发现：

当前代码中的Merge是：

> 同Operation层的数量合并。

新的Execution Batch是：

> 一个MES执行批下面天然包含多个Operation Task。

所以：

> **不能为了支持Execution Batch，就把NC、挤丝、精修三个Operation Task“Merge成一个Task”。**

正确模型：

```text
Execution Batch先确定
↓
沿Routing展开Operation
↓
每道Operation形成独立Task.Id
↓
这些Task共享同一个StageExecutionBatchDraftKey
↓
2号位最终共享同一个TaskNo
```

因此后续代码中至少要区分：

```text
Batch Merge
Operation Task Merge
```

不能共用一个模糊的“Merge”语义。

---

# 二十九、StageExecutionBatchDraftKey：允许复用，但生成规则需补证

同意1/2号位：

```text
StageExecutionBatchDraftKey
StageExecutionBatchQty
```

继续复用，不改名。

同时同意后续Task表增加：

```text
StageExecutionBatchDraftKey NVARCHAR(300) NULL
StageExecutionBatchQty DECIMAL(18,4) NULL
```

列宽300可以接受，不做截断。

但是当前建议：

```text
(LogicalDemandKey, StageCode, BatchOrdinal)
```

只有在：

> 一个Execution Batch永远锚定一个LogicalDemand

时才天然稳定。

而我们的联合方案允许：

```text
一个Execution Batch
承接多个Demand份额
```

所以1/2号位下一版必须证明：

- V1 Batch是否始终有唯一AnchorDemand；
- 如果可以Merge多个LogicalDemand，Key怎样对成员集合保持稳定和可复现。

可以考虑：

```text
PI + Stage + ProductionDepartment + BatchOrdinal
```

或稳定成员集合Canonical Key。

具体技术形态由1/2号位决定，但不能留下多Demand碰撞/漂移风险。

# 三十、StageExecutionBatchQty正式语义

统一定义：

> `StageExecutionBatchQty` = 该Stage执行批的计划净业务数量。

### 新C桶

由1号位Batch Decision形成。

### 已有MES工单的追溯/执行事实

如果未来需要写入，则取原MESWorkOrder.PlannedQty。

它不是：

```text
ExecutionRemainingNetQty
```

也不是：

```text
OperationRemainingNetQty
```

所以即使多个Operation Task共享一个TaskNo：

```text
StageExecutionBatchQty
```

应保持一致；

而：

```text
Task.Quantity
```

在IN_PROGRESS多Slice场景下可以不同。

# 三十一、AllocationTaskShare：2号位必须补评估，不能跳过

TaskNo从“单Task”升级为“一批多Operation Task”以后，必须防止：

```text
同一Demand Share
在NC记500
在挤丝又记500
在精修再记500
→ 汇总成1500
```

2号位下一版必须明确：

> 一个Execution Batch的Demand份额怎样只形成一份权威数量关系。

优先建议评估：

```text
每个Execution Batch只在一个代表Task
（通常Stage最后完成Operation Task）
落权威AllocationTaskShare
```

其它Operation通过：

```text
TaskNo
+
TaskDependency
```

追溯到同一Execution Batch的Demand归属。

如果现有代码已有其它不重复计算的做法，也可以保留。

但必须证明：

```text
AllocationQty
=
Σ 权威AllocationTaskShare
```

不会因一个TaskNo多Operation而重复。

# 三十三、MaxOptimizationSplitCount与MaxBatchCandidates要分开

## MaxOptimizationSplitCount

控制：

> 一个“优化性拆批方案”最多拆成几批。

当前3号位已有默认3。

阶段A先继续保留3，不因1号位建议2直接改冻结值。

## MaxBatchCandidates

控制：

可以新增。

1号位建议6可以作为压测初值。

它是工程搜索预算，不是业务硬批数。

## 强制拆批数量

由硬Max决定。

不受上述两个参数限制。
