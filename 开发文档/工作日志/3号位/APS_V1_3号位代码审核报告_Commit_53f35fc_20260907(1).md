# 五、P0——必须优先关闭

# P0-01 Auth 运行代码与冻结 Auth DDL v1.1 已经物理不兼容

这是本轮最明确的问题。

## 代码事实

当前 `User` 实体使用：

- `UserCode`
- `UserName`
- `Status`
- `FactoryId`
- `DepartmentId`
- `LastLoginTime`
- `LastLoginIP`
- `FailedLoginAttempts`
- `LockoutEnd`
- `RefreshToken`
- `RefreshTokenExpiry`

而项目来源冻结 `Auth DDL v1.1` 的 User 使用：

- `LoginName`
- `DisplayName`
- `IsEnabled`
- `LastLoginAt`

两者已经不是“可忽略命名差异”，而是直接 SQL/EF 无法互通。

当前 `RbacManagementService` 也直接 SQL 访问：

```text
UserCode / UserName / FactoryId / DepartmentId / Status
Role.IsActive / UpdatedAt
Permission.Category / IsActive / UpdatedAt
```

而 v1.1 DDL 并不完整支持这些字段。

## Permission 还存在第二个硬冲突

冻结 DDL 有：

```text
CHECK PermissionCode LIKE 'aps.%'
```

当前 `PermissionCodes` 则是：

```text
plan.view
plan.ctp
candidate.confirm
rule.maintain
...
```

不带 `aps.`。

如果全新执行冻结 v1.1 DDL，再运行当前种子，权限码会直接违反数据库约束。

## 对上传派单的一处事实纠正

派单中写：

> Permission：DDL 无 Module

这一点**不正确**。

当前项目来源 Auth DDL v1.1 已经有：

```text
Module NVARCHAR(50) NOT NULL
ActionType NVARCHAR(50) NOT NULL
```

真正差异是：

- DDL 有 `ActionType`；
- 当前代码改成了 `Category`；
- 代码增加 `IsActive / UpdatedAt`。

说明该派单不能直接作为“DDL全部错、代码全部对”的证据。

## 裁定

> **P0。必须先形成唯一可部署的 Auth Schema。**

但整改方法不是“代码有什么字段就全部写进DDL”，详见本报告第十部分正式裁决。

# P0-02 DomainDefinition / Candidate Run / FAILED Recovery 等高风险写接口只有“登录校验”，缺功能权限

ASP.NET 全局 FallbackPolicy 只保证：

> 用户已登录。

它不等于：

> 用户有权做这个动作。

当前 `GovernanceController`：

### 有功能权限的例子

Rule版本维护：

```text
[Authorize(Policy = RuleMaintain)]
```

Rule发布：

```text
[Authorize(Policy = RulePublish)]
```

Candidate确认/激活：

```text
[Authorize(Policy = CandidateConfirm)]
```

### 但以下高风险端点没有功能权限 Policy

- `POST /domain-definition`
- `PUT /domain-definition/{id}`
- `POST /domain-definition/{id}/enable`
- `POST /domain-definition/{id}/disable`
- `POST /run/candidate`
- `POST /run/{id}/recover`
- `POST /run/{id}/validate-domain-keys`

因此当前实际效果是：

> **任何“已认证用户”都可能发起这些治理写操作。**

这与 V1“功能权限必须后端执行”直接冲突。

## 裁定

> **P0。**

## 最小整改

不建设新权限平台。

只需要把现有 Permission Policy 正确挂到这些正式治理动作：

- DomainDefinition治理；
- Candidate Run创建；
- FAILED恢复；
- 必要的Run治理动作。

权限码最终名称随 Auth v1.2 一次统一，不另开第二套。

# P0-03 Business Scope 没有真正应用到3号位治理写操作

这是比“有没有权限码”更重要的第二层问题。

当前 `PermissionAuthorizationHandler` 只判断：

> 用户有没有目标 PermissionCode。

它不判断：

- Factory；
- ProductFamily；
- Department；
- Domain。

当前 `GovernanceController` 也没有注入/调用 `IDataScopeService` 来限制治理写操作。

所以例如：

- 用户只被授权 Domain=D01；
- 但只要有 CandidateConfirm 权限；

当前接口没有看到后端校验阻止他确认/激活 D02 Candidate。

同样：

- ProductFamily=X 的规则维护者；
- 可能修改 Y 范围的规则/策略；

如果只有功能权限，没有 Business Scope，就无法满足冻结验收 A09/A10。

冻结实施包已明确要求：

- Factory=TJ 用户不能操作 BJ；
- ProductFamily=X 维护者不得修改 Y；
- Domain=D01 用户不得确认 D02 Candidate；
- 手工构造HTTP绕过前端，后端仍必须拒绝。

## 裁定

> **P0。**

## 最小整改

继续复用现有：

```text
DataScopeService
DataScopeContext
```

不要新建 Scope 引擎。

在治理写接口中：

1. JWT → UserId；
2. 功能 Permission；
3. ResolveScope；
4. 根据目标对象解析 Factory/ProductFamily/Domain；
5. 后端拒绝越界；
6. 再进入 Service。

# P0-04 未冻结的第14张 GovernanceAuditLog 已成为正式运行依赖

当前冻结 Auth v1.1 明确：

> 在原13张表基础上增量对齐，不推翻结构。

13张包括：

- 9张正式 Auth/RBAC/Scope/Audit；
- 4张 Approval兼容表。

其中正式审计真值已经有：

> `AuditLog`

但当前代码新增：

> `GovernanceAuditLog`

成为 `AuthDbContext` 第14个 DbSet/物理表。

而且 Candidate人工确认不是只“顺便记日志”，而是：

```text
Confirm Candidate
↓
写 GovernanceAuditLog
↓
Activate Candidate
↓
必须先查询 GovernanceAuditLog 中是否存在 ConfirmCandidate
```

也就是说：

> 一个未进入冻结 Auth DDL 的第14张表，已经成为 Candidate 激活前置业务依赖。

这不是单纯“漏了一张DDL”。

它实质上是：

> **代码自行建立了第二套审计事实，并改变了Candidate确认物理承载。**

## 裁定

> **P0。**

## 最小整改

当前 V1 不应因为代码已经有表，就自动把第14张表冻结下来。

优先方案：

> **把治理审计统一回现有 `AuditLog`。**

Candidate确认也通过统一 AuditLog 表达：

- ActionCode / ActionType；
- ObjectType / EntityType；
- ObjectId；
- Actor；
- 时间；
- 必要附加信息。

只有0号位明确重新打开 Auth Schema 并确认“确有必要建立第二张治理审计表”，才能保留第14表。

本轮不建议这样做。

# P1-04 审计 Actor 仍由请求体 / Query 参数提供，可被调用者伪造

- `request.PublishedBy`
- `request.OperatedBy`

- `entity.CreatedBy`
- `entity.UpdatedBy`

作为审计操作人。

这意味着一个已登录用户可以在HTTP请求中填：

> “操作人=另一个人”。

审计就失去追溯真实性。

## 冻结要求

审计回答的是：

> 谁，在什么时候，对什么对象，做了什么。

所以 Actor 应来自：

> 当前认证 JWT / Current User

而不是浏览器自由填写。

## 裁定

> **P1。**

前端如需展示“备注/代理原因”，可以另字段记录，但真实 Actor 必须后端取身份。

# P1-05 关键治理状态变更与审计不是同一原子闭环

当前多个流程是：

```text
先更新治理对象/PlanVersion
↓
再单独写 GovernanceAuditLog
```

RBAC服务甚至明确把审计定义为：

> best-effort，失败不阻断主流程。

这会出现：

> 规则已经发布 / 权限已经修改 / Candidate已经激活，但审计没写进去。

对普通查询可以接受日志失败，但对：

- 规则发布；
- 权限变更；
- Candidate确认/激活；
- FAILED恢复；
- DomainDefinition变更；

属于关键业务操作。

## 裁定

> **P1。**

不要求建设通用事件总线。

只需保证关键治理写操作：

> 状态变更 + 审计事实

在可实现范围内同事务/同一可靠业务提交边界闭合。

# P2-01 `User.FactoryId / DepartmentId` 与正式 Business Scope 模型重复

当前 `DataScopeService` 已经正确使用：

```text
UserDataScope
RoleDataScope
DataScopePolicy
```

但 `User` 又存在：

- FactoryId；
- DepartmentId；

而且 RBAC CRUD 仍然维护它们。

这会让后续开发AI误以为：

> User.FactoryId / DepartmentId 就是授权范围。

## 处理

本轮不要求为了“表漂亮”立即删除。

但 Auth v1.2 必须明确：

- 它们不是正式 Business Scope 真值；
- 正式授权只认 DataScopePolicy 体系；
- 若无其它真实用途，建议退出正式字段；
- 若保留，只能作兼容/默认展示，不能参与授权决策。

## 8.1 “Auth DDL与代码已经漂移”——同意

这一事实成立。

所以必须形成：

**不需要再找2号位代建或代维护 Auth 库。**

---

## 8.2 “F-G5 = 整个 Auth Schema 的代码真源”——当前不能这样解释

我在当前项目来源和本 Commit 中能核到：

- F-G5 与 RBAC管理实现有关；
- Program 中 F-G5 收尾明确指“代码侧13个功能权限码播种”。

但当前项目来源中**没有找到一份独立、正式、上位于 Auth v1.1 的裁决文件，明确写着：**

> “从此 User/Role/Permission/AuditLog 全部物理Schema无条件以当前代码字段为真源，冻结文档反向追代码。”

因此：

> **不能把 F-G5 从“权限代码/实现收口”扩大解释为“整个 Auth Schema 代码高于冻结文档”。**

如果0号位确实曾口头/其它对话明确作过这一裁决，而尚未进入项目来源，应当在本次 v1.2 重冻结时把裁决正式写进去；在当前可审核基线上，不能靠代码注释自动升级权威等级。

---

## 8.3 “Permission DDL缺 Module”——不同意，属于派单事实错误

当前 Auth DDL v1.1 明确有：

```text
Module NVARCHAR(50) NOT NULL
```

派单这一项需要修正。

真正差异是：

```text
DDL: ActionType
代码: Category + IsActive + UpdatedAt
```

---

## 8.4 “缺 GovernanceAuditLog 是 DDL 缺陷”——不同意

当前冻结 Auth v1.1 明确是13张表，而且已有正式：

> `AuditLog`

代码自行增加 `GovernanceAuditLog` 后，不能反向说：

> “因为代码需要第14张，所以DDL漏表。”

这属于把实现扩展自动升级成冻结业务。

本轮正式裁定：

> **不批准因为当前代码已有 GovernanceAuditLog，就自动把它并入 v1.2。**

优先收敛回统一 `AuditLog`。

---

## 8.5 “现有物理库≈代码”——只能作为开发环境事实，不能当权威证据

派单说集成测试“0 skip”，说明：

> 当前开发测试环境很可能已有代码需要的表/字段。

但这只能证明：

> 某一套测试库能跑。

不能证明：

> 当前物理库Schema就比冻结文档更权威。

数据库结构权威仍必须通过本次 v1.2 重冻结形成，而不是用“测试跑通”代替Schema裁决。
