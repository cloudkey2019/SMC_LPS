## 二、裁定 1：恢复收口 seam —— 抽出既有主体，两个调用方共用

### 2.1 关键事实：你要的 seam 已经存在

`SchedulingOrchestrator.RunSchedulingAutoAsync`（符号锚：方法头注释「排程发令枪」）**逐字就是**「按 Run 多域执行 + 一次性收口」：

| 要素 | 现状（已实现，非待建） |
|---|---|
| 领取粒度 | **按 ScheduleRun**（`WITH (UPDLOCK, READPAST, ROWLOCK)`，`WHERE Status='RUNNING' AND RunType='FULL_SCHEDULE' AND EXISTS(PlanVersion ... Status='Created')`） |
| 域集合来源 | `GetExpectedDomainKeysAsync(scheduleRun.Id)` 读 `ExpectedDomainKeysJson` |
| 多域执行 | `foreach (orderedDomainKeys)` 串行；`OrderDomainsTopologically` 拓扑序；`BuildUpstreamClosure` 依赖感知阻断（**只阻断传递依赖失败上游的下游**，非一刀切） |
| 跨域共享 | `sharedResourceOccupancy` 逐域累积（FULL §9） |
| **一次性收口** | **三态各一次**：全成功 `CompleteAsync` / 部分 `PartialSuccessAsync` / 全失败 `FailAsync` |

⇒ **所以 §二.2 你列的「逐域调用会多次 CompleteAsync/FailAsync」这个风险，在 `RunSchedulingAutoAsync` 里根本不存在** —— 它压根不是逐域收口，是**循环完再收口一次**。你担心的那种写法（拿 `RunSchedulingAndFinalizeAsync` 逐域调）才是错的。

### 2.2 为什么不扩 `RunSchedulingAndFinalizeAsync`

它是**候选单域专用 seam**，带两个候选专有语义：

- `sourcePlanVersionId: run.BasePlanVersionId` —— 需求侧订单钉基线（候选语义，FULL 恢复**不需要**）
- `scope`（`ScopeJsonV2`）—— 候选局部重排范围（FULL 恢复**不需要**）

强行扩展 = 加 mode 开关（坏味道），且**一旦传 null 就会退化成「按本 PV 装订单」**，与 FULL 语义混淆。

### 2.3 裁定与交付形态

**抽出** `RunSchedulingAutoAsync` 的多域主体为独立方法，**夜间发令枪与恢复共用**：

```csharp
/// <summary>
/// 按 ScheduleRun 执行全量排程并一次性收口（RUNNING → COMPLETED / PARTIAL_SUCCESS / FAILED）。
/// 前置：Run 须为 RUNNING，且其 ExpectedDomainKeysJson 中每个 Domain 均存在
///       Status='Created' 且 SourceScheduleRunId=该 Run 的 PlanVersion 壳。
/// 后置：Run 达终态；每个 PV 达 Computed / ComputeFailed。
/// 本方法不抛业务异常（Cancellation 除外），失败以返回结果表达。
/// </summary>
Task<SchedulingRunResult> ExecuteRunAsync(int scheduleRunId, CancellationToken ct = default);
```

- `RunSchedulingAutoAsync` = **「找到该跑的 Run」**（领取 SQL）+ `ExecuteRunAsync`
- 恢复路径 = 3号位 建好壳后**直接调 `ExecuteRunAsync(newRunId)`**

**为什么不复制一份**：该主体约 120 行，含拓扑序、依赖感知阻断、共享资源占用、三态收口 —— 复制 = 两处漂移。这与 2号位 装载层踩过的坑同源（点修不扫全量 ⇒ 两周后别处复发），**能共用就不复制**。

**调用方式（需 3号位 定夺延迟预算）**：建议**内联调用**，与候选路径一致（`CreateCandidateRunAsync` 现状也是内联等执行完）。⚠️ **但请 3号位 确认端点超时预算**：实测 FULL `FAMILY_X` 全量单次 ≈ **5.4 分钟**，多域恢复可能更长。若端点容忍不了：
- **备选（我接受）**：恢复只建壳 + 建 Run 后**立即返回**，把执行交给下一次触发领取 —— 因为 RunType 继承 `FULL_SCHEDULE`、壳是 `Created`，**发令枪领取条件天然成立**，能跑通，只是延迟（夜间触发 02:00，最长等一天）。此时**必须对操作人明示「恢复已排队、非立即」**。

## 三、裁定 2：壳由 3号位 建 —— 但**一域一壳**，且与 Run 同事务

### 3.1 归属：3号位 建

理由（三条，均以既有代码为据）：

1. **同artifact同类，既有模式已定**：候选路径的壳就是 3号位 侧建的，且是**同一事务原子写**（`ScheduleRunRepository.CreateCandidateRunAsync` 内 `ExecuteInTransactionAsync` 写 Run + 壳）。恢复的 Run 也已由 3号位 的 `InsertForRecoveryAsync` 写 —— 把壳并进同一事务最自然。
2. **原子性正是本 bug 的病灶**：`RecoverFailedRunAsync` 自己的注释写着「新建前先校验继承基线合法性（**避免插入后再因基线不合法产生孤立 RUNNING 记录**）」—— 说明你已在意孤立 RUNNING。若壳交给 2号位 后建：壳建失败 ⇒ **RUNNING 无壳**，而发令枪要求「有 Created 壳」⇒ 该 Run **永久领不走 = 永久孤立**（比现在更糟）。
3. **2号位 的 seam 必须保持输入驱动**：`ExecuteRunAsync` 的契约是「按 `SourceScheduleRunId + DomainKey` 找壳」。若 2号位 建壳，就得由 2号位 发明 `VersionCode` / `PlanHorizon` / `CreatedBy` —— 那是运行治理取值，不是执行取值。

### 3.2 ⚠️ 关键修正：**N 个壳，不是 1 个**

候选路径建 **1** 个壳，因为**候选按设计是单域**。**恢复不是** —— FULL_SCHEDULE 恢复可能多域，而 `ExecuteRunAsync` 是**逐 Domain 按 `SourceScheduleRunId=@RunId AND DomainKey=@DomainKey` 解析 PlanVersion** 的。

⇒ **必须对 `ExpectedDomainKeysJson` 里每一个 DomainKey 各建一个壳**，否则多域恢复里除一个域外全部走「预期 Domain 无对应 PlanVersion（装载缺口）」分支被计为失败。

### 3.3 壳形状（逐字段权威取值）

| 字段 | 取值 | 依据 |
|---|---|---|
| `VersionCode` | `RECOVERY_{yyyyMMddHHmmss}_{DomainKey}` | 对齐既有两种格式：`NIGHTLY_{yyyyMMdd}_{DomainKey}` / `CANDIDATE_{DomainKey}_{ts}`。**必须含 DomainKey**（多壳需可区分）+ 时间戳（同日重跑不撞） |
| `VersionCategory` | `'RECOVERY'` | 见 §四 |
| `DomainKey` | `ExpectedDomainKeysJson` 中每个 key | 一域一壳 |
| `Status` | `'Created'` | **发令枪领取条件**逐字要求 `pv.Status='Created'`；`ExecuteDomainAsync` 也从 `Created` 推进 |
| `ComputeMode` | `'FULL'` | 恢复 = 全量重算，非增量 |
| `SourceScheduleRunId` | **新 Run Id** | 执行侧唯一的壳↔Run 关联键 |
| `PlanHorizonStart/End` | **继承失败 Run 的既有 PlanVersion** 的窗口；缺失时兜底「今天 ~ +90 天」 | 恢复应复现原窗口，**不得静默平移**（平移会改变排程结果的可比性） |
| `CreatedBy` | 操作人 / `'Recover'` | 与 Run 的 `TriggeredBy='Recover'` 同源 |
| `BatchNo` | **NULL** | 夜间批专属；恢复无批次 |

## 四、裁定 3：词表取值

### 4.1 `VersionCategory = 'RECOVERY'`（新取值）

**已核全部消费点，新增取值安全。** 全仓 `VersionCategory` 消费点共 7 处（不含 DTO 字段与赋值），**逐条核验**：

| 消费点（符号锚） | 判定 | 对 `'RECOVERY'` 的行为 |
|---|---|---|
| `OverviewQueryRepository` 候选列表 `= 'CANDIDATE'` | 等值 | 不出现 ✓ 正确（恢复不是候选） |
| `ScheduleQueryService` 可见性 `CASE WHEN = 'CANDIDATE' OR Status='ARCHIVED'` | 等值 | 不取候选基线指针 ✓ 可接受 |
| `ScheduleQueryService` 候选对比门禁 `!= "CANDIDATE"` ⇒ throw | 等值 | 拒绝候选对比 ✓ 正确 |
| `ScheduleQueryService` 候选域列表 `= 'CANDIDATE'` ×2 | 等值 | 不混入 ✓ 正确 |
| `RunLifecycleService` 激活门禁 `!= CANDIDATE` ⇒ throw | 等值 | **恢复版本不可被激活** ✓ 正确（恢复重跑不是可激活候选） |
| `RunLifecycleService` 域级待确认 `== CANDIDATE` | 等值 | 不标待确认 ✓ 正确 |
| `SchedulingOrchestrator` 跨域外部占用块 `= 'ACTIVE'` | 等值 | 恢复 Run 的 Task 不作为他域外部块 ✓ 正确（与 DAILY_BASELINE 同待遇） |

**关键安全前提（已实测）**：全仓**没有任何** `VersionCategory <>` / `NOT IN` / 取反消费 —— **全部是等值判定** ⇒ 新增取值**不可能**被既有分支误吞。
（方法沿用 2号位 既有教训：改词表必须**枚举全部消费点**，不能只看「我这侧绿了」。）

**为什么不复用 `'DAILY_BASELINE'`**：① 语义污染 —— `DAILY_BASELINE` 是「夜间全量基线」，恢复重跑**不是**；② `DAILY_BASELINE` 是跨版本连续性 / 基线比对的锚，让恢复版本混进去有被误取为对比基线的风险；③ **新取值成本 = 0**（无约束 NVARCHAR，零 DDL，且已证安全）。**为什么不复用 `'CANDIDATE'`**：会被激活门禁误判为可激活候选，语义直接冲突。

### 4.2 `Status` —— 初值 3号位 写，**终值 2号位 写**（不是你）

- **建壳初值 = `'Created'`**（3号位 写）
- **终值 = 既有执行词表，2号位 的 `ExecuteDomainAsync` 已实现，你不必也不应写**：
  - `'Computing'`（执行中）→ `'Computed'`（成功）／`'ComputeFailed'`（失败 / 被上游阻断）
  - 符号锚：`SchedulingOrchestrator` 的 `UPDATE PlanVersion SET Status='Computing'` / `Status=@Status, ComputedAt=GETDATE()` / `Status='ComputeFailed'`
- **2号位 不新增任何 Status 取值**（`RECOVERY` 只出现在 `VersionCategory`，与 D7 裁决「身份看 VersionCategory、Status 只表达执行进度」一致）

## 五、附带发现（4 项，超出你的三问，但影响恢复正确性）

### 5.1 ⚠️ `InsertForRecoveryAsync` **丢 `BasePlanVersionId`**

`ScheduleRunGov` **有** `BasePlanVersionId` 字段，但 `InsertForRecoveryAsync` 的 INSERT 列清单里**没有它** ⇒ 恢复 Run 的 `BasePlanVersionId` 恒为 NULL。

- 对 FULL 恢复**无害**（FULL 无 Base）
- 但 `RecoverFailedRunAsync` **不限制 RunType** ⇒ **失败候选 Run 也可被恢复**，此时丢 Base ⇒ `ExecuteDomainAsync(sourcePlanVersionId: null)` ⇒ 需求侧订单**不钉基线**、退化为按本 PV 装 ⇒ 候选恢复语义错。

**建议（3号位 自决）**：`InsertForRecoveryAsync` 补 `BasePlanVersionId` 列继承；或在 `RecoverFailedRunAsync` 对**非 FULL_SCHEDULE** 的恢复显式拒绝（更保守）。

### 5.2 ⚠️ `DataCutoffTime` 用 `GETDATE()` 而非继承

`InsertForRecoveryAsync` 写 `DataCutoffTime = GETDATE()`（**新时刻**），未继承失败 Run 的截止时刻。

- 若语义是「复现原跑」⇒ 应继承（否则数据边界漂移、结果不可比）
- 若语义是「用最新数据重试」⇒ 保持 `GETDATE()` 正确，但**应显式写明**（现在是无意为之）

**请 3号位 定语义**（属运行治理口径，我不越位）。我侧不阻塞。

### 5.3 ⚠️ 抽出的 `ExecuteRunAsync` 重入会把已 `Computed` 的域重跑

`RunSchedulingAutoAsync` 解析 PV 时**只按 `SourceScheduleRunId + DomainKey`，不过滤 `Status`**（`Status='Created'` 只出现在**领取 SQL** 里）。⇒ 若同一 Run 被**领取执行一次 + 恢复显式调用一次**，第二个调用会把已 `Computed` 的域**重跑一遍**（结果重写，非损坏，但浪费）。

**2号位 自领**：抽 `ExecuteRunAsync` 时加重入守卫。**这是重构顺带修的，不额外要你配合。**

> **✅ 已实现（2026-09-29），但口径与上面这句不同，请注意**：守卫条件是
> **「全部预期 Domain 的 PV 均已终态 ⇒ 跳过整段执行、只补一次收口」**，
> **不是**「逐域跳过已达终态的 Domain」。理由：逐域跳过会丢掉已成功域的 `sharedResourceOccupancy`
> （FULL §9 跨域资源占用）⇒ 后续 Domain 会排进已被占用的窗口，**比重跑更糟**；
> 全终态跳过时一个 Domain 都不执行，该上下文无人消费，故无此副作用。
> **附带收益**：兜住「全部 Domain 跑完但收口前崩溃」⇒ Run 永久卡 `RUNNING`（那种 Run 否则再也领不走）。
> **⚠️ 边界（不夸大）**：只覆盖**先后调用**，**不覆盖两个调用方同时在飞的并发** —— 那需要执行级锁，未做。
> 若你认为恢复路径会与发令枪并发，请回执告知，我再补执行级锁。

### 5.4 ⚠️⚠️ **插单路径上的 `RUNNING` 孤儿：两条补救路都够不着（P1-03 的同族缺陷，但无任何变通）**

> 本条由用户点名「**插单的时候也是需要执行的**」后专项核查得出。**这条比你问的三点更要紧** ——
> §5.1/§5.2 是「恢复结果不对」，本条是「**根本恢复不了**」。

**代码事实**（`RunLifecycleService.CreateCandidateRunAsync`，即插单/候选排程入口）：

```
// 第 8 步：单事务原子写 Run + 候选壳
  //   ← 该处注释写着「任一失败整体回滚，不产生孤立 RUNNING 运行」

// 第 10 步：正式执行（同一 HTTP 请求内，同步跑完）

        result.NewPlanVersionId, result.NewScheduleRunId, strategyProfileVersionId, ct);
```

**缺陷**：第 8 步的注释只护住了第 8 步。**第 10 步无人兜底** —— 它是一次**同步耗时数分钟**的调用

异常直接穿到 Controller（那里只 catch `InvalidOperationException` → 400），**Run 永久留在 `RUNNING`、壳留在 `Created`**。

**而它两条路都够不着**（均已读码核实）：

| 补救通道 | 前置条件（源码原文） | 能否接走这个 Run |
|---|---|---|

| 恢复端点 `POST run/{id}/recover` | `RecoverFailedRunAsync` 抛异常：**「仅 FAILED 可恢复（旧记录不可回改 RUNNING）」** | ❌ **拒收**（要求恰好是 `FAILED`） |

⇒ **永久卡死**。用户从界面看到的是「这次插单一直转圈 / 永远算不完」，**没有任何按钮能救**，
只能人工上库把 `ScheduleRun.Status` 从 `RUNNING` 改掉 —— 而按你们自己定的规矩**不允许回改 RUNNING**。

**这个缺口是真实的、不只是理论**：插单是**操作人点一下就要等结果**的交互式路径（对比夜间跑没人盯着），
恰恰是最容易被客户端超时 / 网关断连打断的场景；而且 §2.3 里我已经就**恢复端点**提过同一个超时预算问题 ——
**候选端点现在就已经是这个形态了**。

### 6.3 追加（v1.3，读码得出）：两条**直接影响你 §2.3 超时预算**的事实

**① 部分失败的恢复 = 全部 Domain 重跑，恢复耗时 ≈ N × 单域耗时，不是「只补失败那个域」。**

`ExecuteRunAsync` 的循环对 `orderedDomainKeys` **逐个执行、无逐域跳过**；取壳的 SQL 是
`WHERE SourceScheduleRunId=@RunId AND DomainKey=@DomainKey ORDER BY Id DESC`，**不过滤 `Status`**。
⇒ 若某 Run 是「A 成功 / B 失败」，重入时守卫**不会**触发（未全终态），于是 **A 会被再跑一遍**。

**这是有意为之，不是漏判**：逐域跳过会丢掉已成功域的 `sharedResourceOccupancy`（FULL §9 跨域资源占用）
⇒ 后续 Domain 会排进已被占用的窗口，**结果比重跑更糟**（同 §5.3 的理由）。

⇒ **对你的意义**：§2.3 里「超预算则改排队模式」这个判断，**阈值要按 `N × 5.4 分钟` 估，不是 5.4 分钟**。
   多域生产环境下这是十几到几十分钟的同步 HTTP —— **我建议直接按「排队模式」设计**，别赌超时。

**② 我新增了「壳盘点」诊断（`ExecuteRunAsync` 执行前一次 GROUP BY 查询），把缺壳的归因改准了。**

原代码在找不到壳时记 **「装载缺口（装载阶段未创建）」** —— 这个措辞只在**夜间/候选**路径成立；
**恢复路径**缺壳的真实原因是**你的 §3.2 建壳没建全**，却被写成装载问题 ⇒ **会把你引向错误阶段排查**。
现已改为：执行前先盘点该 Run 的壳（`GROUP BY DomainKey`），
- 一次性报出 **缺壳 Domain 清单**、**壳总行数**、
- 并暴露 **「同一 DomainKey 多个壳」**：执行侧取 `TOP 1 … ORDER BY Id DESC`，
  多出来的壳**不会被任何一次执行认领 ⇒ 永久停在 `Created`**（**你的建壳若不幂等就会踩到**，请确保可重入）。

⇒ **对你的意义**：你 §3.2 建壳若有偏差，**日志会直接点名**，不再伪装成装载问题。**这是为你接线准备的**，不需要你配合。
