## 二、R4 权限批量删除口径 —— **选「停用」**

### 决策

→ **`IsActive=false` 停用**（与 R1 清理口径一致），**不做真删**。

### 理由（3 条）

1. **与 R1 一致**：R1 cleanup 端点对权限也是 `IsActive=false` 停用语义（贵方 §一.2 表）。R4 批量删除若改「真删」，**两端点行为分叉**，违反「批量 = 单删 ×N」的预期。

2. **权限码的「软回收」更安全**
   - 停用后：**已挂在角色分配权限上的历史授权继续存在**，但前端任何路径都不会再启用该权限（读侧过滤 `IsActive=true`）
   - 真删会**让 Order/Candidate 等历史数据的 `permission_code` 引用变 NULL**，污染审计日志，且不可恢复
   - 权限码是「字典」性质，**字典不应真删**，只应停用

3. **可逆性**：误删权限码无任何恢复路径（无 PUT 端点改回 Active）；停用则管理员随时可在「权限码」页**改回 Active**（需 3 号位 提供 PUT 端点，或现 deleteUser→reactive 的 workaround）

### 建议贵方在 R4 实现时

- §四.1 末行「或补真删——待贵方确认 UI 需求」**删除该分支**，统一为「停用」
- 4 个批量端点的响应 `failed` 元数据对齐 `{ kind, id, reason }` 结构（用户/角色已用此结构，权限补齐即可）
- 权限批量停用时，若该权限已被某个角色分配（`role.permissions` 关联），保留关联关系，仅 `permissions.isActive=false`（**不需要解绑**）—— 与单删语义对齐

## 三、R2 分页契约微调建议 —— **pageSize 200 上限预留扩展注释**

### 建议（非阻塞）

契约 §二写「pageSize 上限 200（超限按 200 截断）」—— 4 号位 **完全接受**这个硬上限（生产防拉全表必要）。

但建议贵方在 **4 端点 Controller** 各加 1 行 XML 注释（举例）：

```csharp
/// <param name="pageSize">每页条数，默认 20，允许 20/50/100；
///   **当前硬上限 200**（超限截断）。如业务需更大分页（500/1000），
///   仅调整本常量 + 前端 page-size 选项两处，不动契约文档。</param>
```

### 理由

- 后续真有「导出全量数据」需求时（admin 偶尔需要），**改 1 个常量 + 1 个前端选项**即可
- 不动契约 = 不再发新契约文档 = 不重新走「接口即契约」流程
- 注释是「未来变更路径」指引，避免后人误以为 200 是固定业务规则

→ **不强求**；若贵方倾向不加注释，4 号位 也按契约实现即可，不阻塞。
