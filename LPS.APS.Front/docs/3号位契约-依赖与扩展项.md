## 三、详细改动

### ① 【P0】业务 Controller 补 scope 二次校验

**现状**：权限码校验已到位，例如
```csharp
[Authorize(Policy = PermissionCodes.CandidateConfirm)]
[HttpPost("plan-version/{planVersionId}/confirm-candidate")]
```
但**没有**校验该 planVersion 的 `DomainKey` 是否在调用者的 `Domains` 范围内。

**后果**：持 `aps.candidate.confirm` 的 PMC，可以确认**任意 Domain** 的 Candidate——即使他的 DataScopePolicy 只授了 `FAMILY_INJECTION`。前端已拦（[candidate.ts](../src/store/modules/aps/candidate.ts) `assertScope`），但那只是 UX 防御。

**需要补的端点与维度**：

| 端点 | 已有权限码 | 需补 scope 维度 |
|---|---|---|
| `POST /api/governance/plan-version/{id}/confirm-candidate` | ✅ `CandidateConfirm` | `Domains` ∋ planVersion.DomainKey |
| `POST /api/governance/plan-version/{id}/activate-candidate` | ✅ `CandidateActivate` | 同上 |
| `POST /api/governance/rule-set-version/{id}/publish` | ✅ `RulePublish` | `Domains` ∋ ruleSet.DomainKey（`ALL` 放行） |
| `POST /api/governance/rule-set-version/{id}/retire` | ✅ `RulePublish` | 同上 |
| CTP 评估端点 | ✅ `CtpEvaluate` | `Domains` |
| 需求保护释放端点 | ✅ `DemandProtectionRelease` | `Factories` |
| MES 下发端点 | ✅ `MesDispatch` | `Factories` |

**建议实现**：写一个 `IDataScopeService.EnsureInScopeAsync(userId, DataScopeTypes.Domain, domainKey)` 之类的断言方法，在各 Controller 取到业务实体的 DomainKey/FactoryCode 后调用，避免每个 Controller 复制判断逻辑。

**语义约定（与前端 [scope.ts](../src/store/modules/aps/scope.ts) `checkScope` 一致）**：
- `IsGlobal == true` → 全放行
- 对应维度集合为空 → 该维度不限制
- 集合非空且不含目标值 → 拒绝

**统一错误语义**（前端已按此解析）：
```csharp
return StatusCode(403, new { success = false, error = $"业务范围越界（domainKeys）：{domainKey} 不在白名单" });
```

**⚠️ 关于规则发布权**：v1.2 DDL 把原 `RULE_ADMIN` + `RULE_PUBLISHER` 合并成单一 `aps.admin.aps`，所以 §二十五.3「规则管理员不能自动拥有发布权」**无法用角色表达**。现有的 `[Authorize(Policy = PermissionCodes.RulePublish)]` 做法**正确**，请保持，不要改回角色校验。

### ② 【P1】RBAC「读回当前分配」端点

**问题**：现有 18 个端点里，分配相关的**全是写**（`PUT .../roles` / `.../permissions` / `.../scopes`），**没有任何读回接口**：
- `GET /api/rbac/users` 返回 `UserSummaryDto`，**不含** `roleIds`
- `GET /api/rbac/roles` 返回 `RoleSummaryDto`，**不含** `permissionIds` / `scopeIds`

**后果**：前端 AssignDialog 是**覆盖式 PUT**，但无法预勾选现有分配。4 号位当前的降级方案：
- 默认**全不勾选**（错误预勾选会静默删权限，比不勾选危险得多）
- 顶部红色 Alert 明示「本弹窗不代表当前生效配置」
- 提交前二次确认

这对管理员体验很差 —— 每次分配都要凭记忆重勾全部项。

**需要补 3 个 GET**：
```
GET /api/rbac/users/{id}/roles        → RoleSummaryDto[]
GET /api/rbac/roles/{id}/permissions  → PermissionSummaryDto[]
GET /api/rbac/roles/{id}/scopes       → DataScopePolicyDto[]
```
（或等价地：在 `GET /api/rbac/users` / `GET /api/rbac/roles` 的 DTO 里直接带上 id 数组。）

**补齐后 4 号位会做**：AssignDialog 打开时先拉当前分配并预勾选，红条警告降级为普通提示。

## 八、2026-09-12 联调实测新发现（基于 `verify-integration.mjs` 26/26 全绿）

`scripts/verify-integration.mjs` 实测结果：**Domain 路径对齐 7 端点 + RBAC 18 端点 + 自删保护 1 项共 26 断言全部通过**。在跑通过程中暴露 4 项合同实测问题，按严重度排序：

### ① 🔴 P0 — DomainDefinition 实体字段是 int FK，前端 DTO 是 string code（直接 400）

**实测**：`POST /api/governance/domain-definition` 携带 `{ productFamily: 'TEST' }` → 后端 model binder 报 `entity 字段必填`（HTTP 400 ASP.NET ProblemDetails）。

**根因**（[DomainDefinition.cs:46](../../lps/LPS.APS.Core/Entities/APS/DomainDefinition.cs#L46)）：
```csharp
public int ProductFamilyId { get; set; }   // int FK，不是 string code
public int? FactoryId { get; set; }        // int FK，不是 string code
```

**前端 DTO**（[types/domain.ts](../src/api/aps-v1/types/domain.ts)）：
```ts
productFamily: string   // ❌ 后端要 int
factory?: string         // ❌ 后端要 int?
```

**影响**：Domain 维护页保存按钮在生产模式下 100% 失败。当前 mock 模式不感知（fixture 字段自洽）。

**两条修复路径**（需 3 号位决策）：
- **方案 A（推荐）**：前端 DTO 改成 `productFamilyId: number; factoryId?: number`，Domain 维护页新增 ProductFamily / Factory 选择器（调现有接口或新建 `GET /api/governance/product-families` / `factories`）
- **方案 B**：后端 DTO 加 `[JsonConverter]` 接受 string code 自动转 int（侵入小但需写自定义转换器）

**3 号位请定方案 + 补 `GET /api/governance/product-families` 与 `GET /api/governance/factories` 端点**（前端维护页需要下拉数据源）。

### ② 🟡 P1 — `Role.RoleCode` / `Permission.permissionCode` 有 `aps.` 前缀 CHECK 约束

**实测**：POST `/api/rbac/roles` body `{roleCode: "verify.role.xxx"}` → `code:500`，错误日志：
```
INSERT 语句与 CHECK 约束"CK_Role_RoleCode"冲突。
   ...APS_Auth, dbo.Role, column 'RoleCode'
```

**根因**：DDL 约束要求 `aps.` 前缀（与 4 个 seed 系统角色码 `aps.admin.system` / `aps.planner` 等一致）。

**前端表现**：RbacRoles.vue 的"新建角色"表单未做前缀校验，用户填 `verify` 提交会 500 弹原码错误。前端应在表单层加 `pattern: /^aps\..+/` 实时校验 + 错误提示。

**3 号位需补**：
- 在 `CreateRoleRequest` 加 `[RegularExpression("^aps\\..+")]`（422 + 中文 message，比 500 友好）
- `Permission.permissionCode` 同理（实测 `aps.verify.xxxx` 成功，`verify.xxxx` 也会 500）

### ③ 🟢 P2 — `GovernanceController` POST 返回 HTTP 201，与 RBAC 的 HTTP 200 不一致

**实测**：`POST /api/governance/domain-definition` → HTTP 201 + `CreatedAtAction(...)`，body 无 `code` 字段（直接是 `{success:true, data:{...}}` 包裹）。

**影响**：前端 `apsHttp` 当前用 `json.code !== 200` 判定失败，会**误判 201 为失败**抛 ApiError。Domain 保存实际可能 OK 但 UI 弹红。

**修法**（任一）：
- 前端 `http.ts` 把 `code === 201` 当成功（推荐，与 RESTful 语义一致）
- 后端统一包 `ApiResponse<T>`（更彻底，但要改 GovernanceController 多个端点）

### ④ 🟢 P2 — `GovernanceController` 响应包装与 RBAC 不一致

**实测对照**：

| Controller | 成功响应 | 失败响应 |
|---|---|---|
| `RbacController` | `{code:200, message, data, timestamp}` | `{code:4xx, message, data:null, timestamp}`（HTTP 200） |
| `GovernanceController` | `{success:true, data}` | `{success:false, error}`（HTTP 4xx 如 400 / 404） |

**影响**：`apsHttp` 当前的解包逻辑假设所有 Controller 都用 `ApiResponse<T>`。访问 Governance 端点时，`data` 字段在 body 内的嵌套层不同（`json.data` 是真实数据，`json.code` 不存在 → 默认 200 通过 — 巧合可用但语义不一致）。

**3 号位请决策**：是否把 GovernanceController 也统一包 `ApiResponse<T>`？还是前端为两套包装分别写解包？
