### 当前实际接口契约（后端已实现）

**请求体** `DemandProtectionReleaseRequest`：

```json
{ "lockIds": [1, 2, 3], "releasedBy": "xxx", "releaseReason": "xxxxx" }
```

**响应体** `List<DemandProtectionReleaseResult>`（逐 lock 返回，与请求 lockIds 一一对应）：

```json
[
  { "lockId": 1, "demandKey": "ORDER_...", "status": "RELEASED", "failureReason": null },
  { "lockId": 2, "demandKey": "", "status": "FAILED", "failureReason": "STRICT_BINDING类型不可释放" }
]
```

### ⚠️ 与4号位前端 DTO 的差异（需对齐）

契约文档 §五 的前端 DTO 是「单条聚合结果」，当前实现是「逐 lock 列表」。差异点：

| 项 | 4号位前端 DTO（契约） | 5号位当前实现 |
|---|---|---|
| 请求体字段 | `demandKey` + `lockIds` + `reason` + `actor` | `lockIds` + `releasedBy` + `releaseReason`（无 demandKey/actor） |
| 响应结构 | 单条 `ReleaseDemandProtectionResult` | `List<…>` 逐 lock |
| 响应字段 | `demandKey` / `releasedLockIds` / `releasedAt` / `releasedBy` / `status` / `affectedSupplyKeys?` | `lockId` / `demandKey` / `status` / `failureReason` |
| lockIds 归属校验 | 有「lockIds ⊆ demandKey」校验 | 未做 demandKey 归属校验（请求无 demandKey） |

**原因**：问题③的最终契约是与 2号位 对齐的（释放=置 Status=RELEASED，逐 lock 部分成功），与 4号位先行扩展的前端 DTO 存在命名/结构差异。

**请4号位二选一**：

1. 4号位前端 DTO 对齐当前后端（逐 lock 列表 + `releasedBy`/`releaseReason`）；或
2. 5号位把端点改成契约里的单条聚合结构（`demandKey + releasedLockIds + releasedAt + releasedBy + status`）——需 2号位 确认 releasedAt/releasedBy 回传口径。

## ④ ProcurementManualEtaOverride 加 DepartmentCode（P1，已完成）

| 层 | 文件 | 改动 |

### 当前接口契约

- **列表查询** `GET /api/procurement-manual-eta` 新增查询参数：`departmentCodes=INJECTION_DEPT,MACHINING_DEPT`（逗号分隔多值，可选，不传则不过滤）
