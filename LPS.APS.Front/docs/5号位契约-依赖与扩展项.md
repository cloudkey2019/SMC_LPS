### ⑤ DemandProtection POST release 端点

**位置**：[LPS.APS.Web/Controllers/DemandProtectionController.cs](../../lps/LPS.APS.Web/Controllers/DemandProtectionController.cs)（GET list + POST release 均已落地）

#### POST `/api/demand-protection/release` — 释放

**请求体**（JSON，per-lock 处理，不带 demandKey）：
```typescript
{
  lockIds: number[]        // 要释放的 lockIds（5 号位按 lockId 反查 owner DemandKey；不限制来源 demandKey）
  releasedBy: string       // 操作人（来自前端 user.userCode）
  releaseReason: string    // 释放原因（必填，trim 后非空）— ⚠️ 2026-09-15 后端实况冲突见 §十
}
```

**响应**（`ApiResponse<List<DemandProtectionReleaseResult>>` — **per-lock 部分成功**）：
```typescript
{
  code: 200,
  message: 'success',
  data: [
    { lockId: 9001, demandKey: 'ORDER_xxx', status: 'RELEASED' },
    { lockId: 9002, demandKey: 'ORDER_xxx', status: 'FAILED', failureReason: 'STRICT_BINDING 严格绑定锁不支持手工释放' },
    { lockId: 9999, demandKey: '',         status: 'FAILED', failureReason: 'Lock 不存在' }
  ]
}
```

**前端契约变化**（vs 2026-09-02 初版）：
- ❌ **不再传 `demandKey`**：后端按 lockId 反查 owner DemandKey；前端可一次释放跨 DemandKey 的多个 lock
- ✅ **per-lock 部分成功**：`List<ReleaseResult>` 而非聚合对象；前端按 lockId 联动本地 list
- ✅ **failureReason**：RELEASED 时无；FAILED 时说明原因

**5 号位实现逻辑**：
1. 校验 `lockIds` 非空 + `releaseReason.trim() !== ''` + `releasedBy !== ''`  — ⚠️ **不应包含 ≥5 字符硬约束**（@see §十 2026-09-15 P0 冲突）
2. 按 lockId 逐条反查 owner DemandProtection（不依赖前端传入 demandKey）
3. scope 校验（owner.factory 是否在当前用户 scope 内）
4. 调 [2 号位 `IDemandSupplyHardLockRepository.ReleaseLocksAsync(IEnumerable<long> lockIds, string releasedBy, string releaseReason, CancellationToken)`](../../lps/LPS.APS.Core/Interfaces/IDemandSupplyHardLockRepository.cs)
5. 返回每条 lock 的处理结果

**必加鉴权**：
```csharp
[Authorize(Policy = PermissionCodes.DemandProtectionRelease)]  // 对应 aps.demand_protection.release
[HttpPost("release")]
public async Task<ApiResponse<List<DemandProtectionReleaseResult>>> Release(...) { ... }
```

**4 号位职责边界**（不变）：
- 4 号位**只提交**：`lockIds + releasedBy + releaseReason`
- 4 号位**不计算**：`lockedQty` / `status` 派生
- 4 号位**不写锁表**：转发给 2 号位 Service
